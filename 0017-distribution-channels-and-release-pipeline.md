# ADR-0017: Distribution channels and the release pipeline

**Status**: Accepted (by authorizing phase 0 on this pack, 2026-09-12)
**Date**: 2026-09-12
**Authors**: Md. Sazzad Hossain Sharkar
**Decided by**: Md. Sazzad Hossain Sharkar, Principal Architect

## Context

`reserve` releases by hand from the Principal Architect's machine through `tools/release.sh` (publish core then binary to crates.io, `dist build` for six targets, GitHub Releases on two repositories, yank support) with cargo-dist 0.32.0 shell and PowerShell installers; it has no Homebrew tap, no SBOM, no artifact signature, and no license inventory. cargo-dist also generates Homebrew formulas and npm installers; its 0.33.0 GitHub release (2026-09-11) is not on crates.io, where 0.32.0 is the latest and is what `cargo install` resolved on 2026-09-12. MCP clients expect a binary on PATH (stdio), Claude Desktop can install an MCPB bundle, and the MCP Registry lists servers by `cargo` (crates.io) or `mcpb` (GitHub Releases) package type under `io.github.<org>/<name>`. macOS requires notarization for a smooth first run. How does OwnPG reach a user's machine?

## Decision Drivers

- One command per platform, and a bundle for Claude Desktop.
- Reuse `reserve`'s pipeline and add what it lacks rather than building a new one.
- Provenance a user can verify: checksums, signatures, SBOM, attestation.
- A registry entry under the organization namespace.

## Options Considered

### Option A: reserve's pipeline plus tap, npm, MCPB, registry, SBOM, signing

Channels: `cargo install ownpg --locked` (crates.io), `cargo binstall ownpg` (resolves GitHub Releases), the cargo-dist shell and PowerShell installers, `brew install devops-infinity/tap/ownpg` (a `homebrew-tap` repository generated by cargo-dist), an npm installer package generated by cargo-dist for Node-centric users, a per-platform `.mcpb` bundle (manifest v0.4, `server.type: "binary"`, `user_config` with `sensitive: true` for the password), and a registry entry `io.github.devops-infinity/ownpg` with `mcpb` packages first and `cargo` added once a test publish proves production acceptance. Targets: reserve's six plus `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl` (eight in all, decided 2026-09-12); the Linux and Windows triples cross-build the libpg_query C code through `cargo zigbuild` and `cargo xwin`. Pipeline: copy `tools/release.sh` and `tools/reinstall.sh`, `ci.yml` and `release.yml` with SHA-pinned actions; add `about.toml` and `cargo about generate` (license inventory), `cargo cyclonedx` (SBOM attached to the release), `cargo auditable build`, a `minisign` signature over `sha256.sum` (every release is built by hand on the Principal Architect's machine, ADR-0020, so GitHub provenance attestations do not apply), macOS `codesign --options=runtime` plus `notarytool` on the zip, and Windows signing when a certificate exists. Fix `reserve`'s CHANGELOG link-reference gap in the copied script.

- Pros: every channel a client expects; the pipeline is already proven in `reserve`.
- Pros: the signature, the SBOM, and `cargo auditable` close the blueprint's supply-chain items.
- Cons: notarization needs an Apple Developer ID; the tap and the registry need organization-level permissions.

### Option B: crates.io only

- Pros: zero release engineering.
- Cons: every user needs a Rust toolchain; no Claude Desktop bundle; no registry listing.

### Option C: GitHub Releases only, no crates.io

- Pros: no crate publishing.
- Cons: `cargo install` users lose out; `registryType: cargo` becomes impossible; the exemplar publishes crates.

### Option D: Do nothing

- Cons: no artifact reaches a user.

## Decision

We will reuse `reserve`'s hand-run release pipeline and cargo-dist packaging, add a Homebrew tap, an npm installer, MCPB bundles, a registry entry under `io.github.devops-infinity`, a license inventory, a CycloneDX SBOM, `cargo auditable` metadata, a `minisign` signature over the checksum file, and macOS notarization, for eight targets.

Option A won because it delivers every install path the clients expect while spending almost nothing on new pipeline code.

## Consequences

- Positive: `brew install devops-infinity/tap/ownpg` and a double-click MCPB cover the two most common user paths.
- Positive: a user can verify the checksum file with the published `minisign` key and read the SBOM.
- Negative: three organization repositories (`ownpg`, `ownpg-releases`, `homebrew-tap`) and one registry namespace need Owner rights.
- Negative: notarization and Windows signing need credentials that never enter the repository or a session.
- Neutral: the npm installer is a convenience, not the primary path, and it is still part of the 1.0 gate.

## Reversibility

Cheap to reverse per channel: each is a configuration block in `[workspace.metadata.dist]` or a step in `release.sh`.
