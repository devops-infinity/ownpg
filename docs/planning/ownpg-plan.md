# OwnPG Implementation Plan

**Audience:** the Principal Architect and the engineering sessions that build OwnPG (human or agent), plus anyone reviewing the build order
**Purpose:** turn the PRD and the twenty ADRs into an ordered, checkable build with entry and exit gates per phase, so each session knows what to do next and how to prove it
**Out of scope:** product requirements (see `ownpg-prd.md`), the reasoning behind each choice (see the ADRs), research evidence (see `ownpg-research-report.md` and `research/`), and any git operation, which the Principal Architect performs himself
**Last updated:** 2026-09-12 (session September 12th 2026, 01:39:06 PM, GMT+06:00; revised the same day after the blueprint review and the eleven decisions)

## 1. How this plan runs

- Target folder: `/Users/sharkar/Git-Repositories/ownpg`. Source repository `https://github.com/devops-infinity/ownpg` (private). Public repository `https://github.com/devops-infinity/ownpg-releases` for release artifacts, the Homebrew formula source, and bug reports (ADR-0020). The Principal Architect creates both repositories; sessions never run `git init`, `git commit`, `git push`, or `git tag`.
- The build follows the `rust-cli-apps` skill in scaffold mode with `reserve` as the exemplar: `/rust-cli ownpg /Users/sharkar/Git-Repositories/ownpg --scaffold --exemplar /Users/sharkar/Git-Repositories/reserve`. Crate internals follow the `rust-modules` skill. Every phase ends with `/audit` on the changed paths and `/hunt` on the safety-critical ones (classifier, connection, renderer, HTTP auth).
- Every dependency is added with `cargo add <crate>` at the moment of use, resolved to the latest release by cargo, checked on crates.io for existence and publisher, and recorded in `Cargo.lock` in the same session. No version number in this plan or the research report is typed into `Cargo.toml` by hand. A crate enters the workspace in the phase that first calls it, so `cargo machete` never flags an unused dependency.
- `anyhow` is not used; the library and the binary share one error type with `ExitClass` and `ErrorId` (ADR-0005).
- Tests come first for every behavior the PRD names; the acceptance criteria in PRD section 9 are the test list.
- Sizes below are relative (S, M, L, XL) and describe scope, not time. Nothing in this plan estimates hours or days.
- Phases map to the PRD milestones M0 through M5. A phase is done when its exit gate passes with command output as evidence.
- Release artifacts are built by hand on the Principal Architect's machine through `tools/release.sh`, as `reserve`'s are (ADR-0020). GitHub Actions runs the checks and the container jobs; it never publishes a release.
- The project stays in development until the Principal Architect declares the tool stable (his instruction of 2026-09-12): the workspace version stays at 0.1.0, nothing is tagged, nothing is published to crates.io, no GitHub release is created, and every completed phase is recorded under `[Unreleased]` in `CHANGELOG.md`. The phase milestones M1 through M5 in the PRD are gates, not releases. Work lands on the `sazzad/ownpg-development` branch of the private repository, one commit per finished work item or phase, and a pull request to `main` stays open for him to merge when he chooses.
- Development-machine tools installed on 2026-09-12 for this plan: `cargo-dist` 0.32.0 (the crates.io latest; the 0.33.0 GitHub release is not on crates.io), `cargo-binstall` 1.23.0, `cargo-cyclonedx` 0.5.9, `cargo-auditable`, `cargo-semver-checks` 0.50.0, `cargo-llvm-cov` 0.9.1, `cargo-insta` 1.48.0, `hadolint` 2.15.1. SSH tunnel tests run against an in-process `russh` server started by the test itself, so no `sshd` and no container is needed anywhere. ## 9. Parallel work and sequencing

- Phase 0 is sequential and small.
- In phase 1, items 1.3 (configuration), 1.5 (SSH), 1.7 (classifier), and 1.12 (audit) are independent of each other and can run as parallel sessions with separate modules once 1.1 and 1.2 land; 1.4 depends on 1.3; 1.8 through 1.11 depend on 1.4 and 1.7.
- In phase 2, the renderer (2.3) gates every tool; 2.4, 2.5, and 2.6 can run in parallel after it; 2.7 is independent.
- In phase 3, 3.1 through 3.4 are independent.
- In phase 4, 4.1 gates 4.2; 4.3 is independent.
- Two parallel sessions never edit the same file; each owns its handler modules and tests.

## 10. Risks that change the order

- If a release triple cannot build the libpg_query C code on the development machine in phase 0, that triple is deferred in ADR-0019 and the plan continues with the rest; report to the Principal Architect with the compiler output.
- If rmcp issue #1261 reproduces in 1.11 and has no workaround, stdio release waits and the HTTP test rig carries the conformance work meanwhile; report to the Principal Architect with the failing test.
- If `pg_query` cannot parse a PostgreSQL 18 statement the tests need, the parse-failure policy (ADR-0009) applies and the README lists the affected syntax; when PR #79 ships, bump and remove the exceptions.
- If the registry rejects `cargo` in 5.3, ship `mcpb` only and retry at the next release.
- If notarization credentials are not available for 5.1, ship unsigned macOS zips with the checksum and the `minisign` signature and document Gatekeeper's prompt; add notarization when the certificate exists.
- If PostgreSQL 19 reaches GA during phase 3 or later, add it to the CI matrix as a supported version in the same phase and re-read its release notes for reverted items.
- The development machine cannot run Docker; every gate that needs a container (the PostgreSQL version matrix, the image build) lives in GitHub Actions only, and the local gate uses the Homebrew PostgreSQL and in-process servers. A phase never waits on a local container.
