## 1. What this report answers

OwnPG is a single MCP server that gives an AI client the whole PostgreSQL DBA lifecycle for one database and one schema: schema, table, column, index, constraint, view, function, and role management, row-level CRUD, exploration, ad-hoc queries, EXPLAIN, maintenance, and monitoring. It runs first as a local stdio server against a local PostgreSQL (Homebrew on macOS, Docker, native Linux packages, Postgres.app, or a server behind SSH), with the user's own credentials, with or without a password. A remote mode over Streamable HTTP with authorization comes second. The user picks read-only, write-only, or read-write access.

Six research workers ran in parallel on 2026-09-12, one per area, each at the web-research skill's search floors, and a seventh worker mapped the `reserve` repository as the local exemplar for the CLI lifecycle and release automation. This report answers eight questions: which MCP revision to build against, which Rust SDK and crates to use, what the existing PostgreSQL MCP servers do and where they failed, how to connect to PostgreSQL from Rust in every hosting setup the brief names, what the current PostgreSQL release state and DBA surface are, how to design tools and secure the server, how each client is configured and how the binary is shipped, and what OwnPG lifts from `reserve`.

## 2. Headline findings

- The current MCP specification revision is `2026-07-28`, released as a stable GitHub release on 2026-07-28T16:47:49Z. It is a breaking rewrite: the protocol is stateless, the `initialize` handshake and `Mcp-Session-Id` are gone, every request carries its version and capabilities in `_meta`, and servers must implement `server/discover`. The draft that follows it holds no changes as of the main branch on 2026-09-08. Source: https://modelcontextprotocol.io/specification/2026-07-28/changelog (2026-07-28) and https://github.com/modelcontextprotocol/modelcontextprotocol/releases/tag/2026-07-28. Confidence: High.
- The official Rust SDK, `rmcp` 3.3.0 (published 2026-09-10, Apache-2.0, MSRV 1.88, edition 2024), implements `2026-07-28` and stays compatible with `2025-11-25` and earlier. The Rust SDK was promoted to Tier 1 on 2026-08-21 with 100 percent conformance on both dated suites. Every alternative Rust crate is stale, tiny, alpha, or community-run. Source: https://crates.io/api/v1/crates/rmcp and https://github.com/modelcontextprotocol/modelcontextprotocol/pull/3287. Confidence: High.
- `rmcp` does not do server-side OAuth. Its `auth` feature is client-side only, so OwnPG owns bearer validation, audience checks, the RFC 9728 protected-resource-metadata document, and the `WWW-Authenticate` challenge as axum middleware in remote mode. Source: `crates/rmcp/src/transport/auth.rs` and `examples/servers/src/complex_auth_streamhttp.rs` at tag `rmcp-v3.3.0`. Confidence: High.
- Every keyword or regex read-only guard surveyed has been bypassed in 2026: DBHub (CVE-2026-61788, 2026-06-24), AWS Labs (CVE-2026-85787 and the critical CVE-2026-87911, September 2026), pgEdge (2026-09-03), pgAdmin's AI Assistant (CVE-2026-12045, CVE-2026-17351), and Postgres MCP Pro's parser allowlist (CVE-2026-85620, still unfixed). AWS replaced its regex with a fail-closed allowlist on PostgreSQL's own parser (libpg_query) on 2026-09-11; Microsoft deleted its blocklists the same day and made the database role the authority. Source: https://aws.amazon.com/security/security-bulletins/2026-101-aws/ (2026-09-04), https://github.com/awslabs/mcp/pull/4575, https://github.com/microsoft/mcp/pull/3202. Confidence: High.
- No Rust PostgreSQL MCP server surveyed parses with PostgreSQL's own grammar; they use `sqlparser` (a generic parser) or keyword checks. The `pg_query` crate (6.2.0, 2026-08-03) binds libpg_query with the PostgreSQL 17 grammar; PostgreSQL 18 grammar support is an open pull request. This is the gap OwnPG fills. Source: https://github.com/pganalyze/pg_query.rs/blob/main/CHANGELOG.md (2026-07-29). Confidence: High.
- The driver is `tokio-postgres` 0.7.18 (2026-06-12, MSRV 1.85). Its simple query protocol returns every column as text and keeps statement framing, which arbitrary DBA SQL needs; `sqlx` 0.9.0 asks for binary output on every column (fails on catalog types such as `aclitem`), wraps multi-statement scripts in an implicit transaction, and declares MSRV 1.94. `tokio-postgres` reads no `PG*` environment variables, `.pgpass`, or service file, so OwnPG implements that loader itself from the PostgreSQL manual. Source: https://docs.rs/tokio-postgres/latest/tokio_postgres/struct.Client.html and https://github.com/rust-postgres/rust-postgres/issues/729. Confidence: High.
- SSH goes in-process through `russh` 0.63.3 (2026-09-09, Apache-2.0, MSRV 1.89): open a `direct-tcpip` channel, turn it into a stream, and hand it to `tokio_postgres::Config::connect_raw`. Shipping Rust PostgreSQL tools (`rpg`, `ferox`) do the same. Only DBHub among the surveyed MCP servers offers SSH at all. Source: https://docs.rs/russh/latest/russh/struct.Channel.html. Confidence: High.
- PostgreSQL 18 is current (18.6 released 2026-08-13, GA 2025-09-25, supported to 2030-11-14). PostgreSQL 19 is at Beta 3 with Beta 4 due 2026-09-24 and no GA date. Supported majors: 18.6, 17.11, 16.15, 15.19, 14.24. Source: https://www.postgresql.org/support/versioning/ and https://wiki.postgresql.org/wiki/PostgreSQL_19_Open_Items. Confidence: High.
- A `READ ONLY` transaction blocks writes and DDL but still allows `SET`, `LISTEN`, `NOTIFY`, `VACUUM`, `ANALYZE`, `REINDEX`, `CLUSTER`, `CHECKPOINT`, `CALL`, `DO`, and even `ALTER SYSTEM`, and it cannot stop a function with side effects. Read-only mode therefore needs three layers together: a role with only the needed grants, parser-based classification, and per-call engine controls. Source: https://www.postgresql.org/docs/18/sql-set-transaction.html plus `src/backend/tcop/utility.c` on `REL_18_STABLE`. Confidence: High.
- Token cost is the top user complaint about database MCP servers. DBHub ships 2 tools at 1.4k tokens against 19.0k for the 28-tool Google Toolbox and 19.3k for Supabase. Claude Code truncates a tool result at 25,000 tokens by default and defers MCP tool schemas behind tool search. Source: https://github.com/bytebase/dbhub (README) and https://code.claude.com/docs/en/mcp. Confidence: High.
- Confirmation for destructive statements cannot rely on elicitation alone: the last official client matrix (2026-05-26, since deleted) lists elicitation for Claude Code, Cursor, Codex, VS Code, and Copilot CLI, and not for Claude Desktop, claude.ai, Gemini CLI, Windsurf, or Zed. OwnPG therefore needs an explicit `confirm` argument and a dry-run path as the baseline, with the 2026-07-28 multi-round-trip elicitation as an upgrade. Source: https://github.com/modelcontextprotocol/modelcontextprotocol/blob/87993a68/docs/clients.mdx. Confidence: High on the snapshot, stale by design.
- Anthropic's connector review requires every tool to carry a `title` and either `readOnlyHint: true` or `destructiveHint: true`, caps tool names at 64 characters, and rejects a catch-all query tool with a `method` parameter. Source: https://claude.com/docs/connectors/building/review-criteria (retrieved 2026-09-12). Confidence: High.
- `reserve` already carries a complete, tested Rust CLI skeleton and release pipeline that OwnPG copies: workspace layout, lint deny-list, clap tree with `config`, `doctor`, `man`, and `completions`, the `Origins` provenance layer, the exit-class error contract, stdout and stderr discipline, the eight-command gate, SHA-pinned CI, `tools/release.sh` and `tools/reinstall.sh`, and cargo-dist packaging. It lacks a license inventory, an SBOM, artifact signing, a Homebrew tap, and a real config-file layer; OwnPG adds those. Source: `research/07-reserve-reuse-map.md` with `path:line` evidence. Confidence: High.

### 3.2 What changed versus 2025-11-25

All items are quoted or paraphrased from https://modelcontextprotocol.io/specification/2026-07-28/changelog (2026-07-28, Authoritative, Confidence High).

- Sessions removed (SEP-2567): no `Mcp-Session-Id`; list results no longer vary per connection; servers that need cross-call state return explicit, server-minted handles as ordinary tool arguments.
- Stateless core (SEP-2575): no `initialize` or `notifications/initialized`; every request carries `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities` in `_meta`; clients should send `clientInfo`, servers should return `serverInfo`; version mismatch returns `UnsupportedProtocolVersionError`.
- `server/discover` is mandatory: it advertises supported versions, capabilities, identity, and instructions.
- `subscriptions/listen` replaces the HTTP GET stream and `resources/subscribe`; clients opt in to change-notification types.
- `ping`, `logging/setLevel`, and `notifications/roots/list_changed` are removed; log level is per request through `io.modelcontextprotocol/logLevel`, and a server must not emit `notifications/message` for a request without it.
- Tasks moved to the official extension `io.modelcontextprotocol/tasks` (SEP-2663): `resultType: "task"`, polling through `tasks/get`, `tasks/update` for input, `tasks/cancel`; no `tasks/list` or `tasks/result`.
- Multi Round-Trip Requests (SEP-2322): server-to-client requests (roots, sampling, elicitation) now ride inside an `InputRequiredResult` (`resultType: "input_required"`, `inputRequests`, opaque `requestState`), and the client retries the original call with `inputResponses`. Every result carries a required `resultType`.
- SSE resumability and `Last-Event-ID` are removed; a broken stream loses the in-flight request and the client re-issues it.
- Minor: `extensions` maps on both capability objects; OpenTelemetry `traceparent`, `tracestate`, `baggage` in `_meta` (SEP-414); tools/list should be deterministic; `Mcp-Method` and `Mcp-Name` headers required on Streamable HTTP POSTs (SEP-2243) plus `x-mcp-header` parameter mirroring; `ttlMs` and `cacheScope` required on `tools/list`, `prompts/list`, `resources/list`, `resources/read`, `resources/templates/list`, and `server/discover` (SEP-2549); resource-not-found is `-32602`; `iss` validation per RFC 9207 (SEP-2468); `application_type` required in dynamic registration; `inputSchema` and `outputSchema` may use any JSON Schema 2020-12 keyword and `structuredContent` may be any JSON value (SEP-2106); error codes renumbered (`HeaderMismatch` -32020, `MissingRequiredClientCapability` -32021, `UnsupportedProtocolVersion` -32022).
- Deprecated with a twelve-month floor (earliest removal on or after 2027-07-28): Roots, Sampling, and Logging (SEP-2577); HTTP+SSE transport reclassified as Deprecated (SEP-2596); dynamic client registration (RFC 7591) deprecated in favor of Client ID Metadata Documents.
- Unchanged: `ToolAnnotations` still carries `title`, `readOnlyHint` (default false), `destructiveHint` (default true), `idempotentHint` (default false), `openWorldHint` (default true), read from `schema/2026-07-28/schema.ts` line 1912. JSON-RPC batching was already removed in `2025-06-18`.

### 3.3 Transport rules a server must follow

- Streamable HTTP: one endpoint that supports POST; the client sends `Accept: application/json, text/event-stream`; a notification gets `202 Accepted`; a request gets either a JSON object or a request-scoped SSE stream; the server never sends independent requests on that stream; the final response should end the stream; `X-Accel-Buffering: no` and periodic SSE comment keep-alives are encouraged; closing the SSE stream is cancellation. Every POST must carry `MCP-Protocol-Version` matching the body's `_meta` value (400 with -32020 on mismatch), `Mcp-Method` on every request, and `Mcp-Name` on `tools/call`, `resources/read`, and `prompts/get`. Unknown method: 404 with -32601. GET or DELETE: 405. `Mcp-Session-Id` and `Last-Event-ID`: ignored. Servers must validate `Origin` (403 on mismatch), should bind to 127.0.0.1 when local, and should authenticate every connection. Source: https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http. Confidence: High.
- stdio: newline-delimited JSON-RPC on stdout, nothing else on stdout, logs on stderr, exit promptly on EOF; cancellation is `notifications/cancelled`; a dual-era client probes with `server/discover` and falls back to `initialize` on any non-modern error or a timeout. Authorization does not apply to stdio; credentials come from the environment. Source: https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio. Confidence: High.

### 3.4 Authorization for HTTP transports

- The server is an OAuth 2.1 resource server. It MUST publish Protected Resource Metadata (RFC 9728) naming at least one authorization server, MUST validate that tokens were issued for it (RFC 8707 audience), MUST NOT accept or pass through any other token, answers 401 with `WWW-Authenticate: Bearer resource_metadata="..." scope="..."`, and 403 `insufficient_scope` for step-up. Clients must use PKCE S256 and refuse a server without it, must record and validate `iss`, and prefer Client ID Metadata Documents (an `https` URL with a path serving `client_id`, `client_name`, `redirect_uris`) over dynamic registration. Source: https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization and its client-registration and security-considerations pages. Confidence: High.
- Two stable auth extensions exist: Enterprise-Managed Authorization (`io.modelcontextprotocol/enterprise-managed-authorization`, ID-JAG cross-app access, Okta first) and OAuth Client Credentials for machine-to-machine use. Source: https://modelcontextprotocol.io/extensions/auth/overview. Confidence: High.

### 3.5 Server primitives, in the shape OwnPG will use them

- Tools: `name` (1 to 128 characters, ASCII letters, digits, underscore, hyphen, dot), `title`, `description`, `icons`, `inputSchema` (a JSON Schema object; no-parameter tools declare `{"type": "object", "additionalProperties": false}`), `outputSchema`, `annotations`. Structured results go in `structuredContent` and should also be serialized into a text block for older clients. Execution errors are `isError: true` results with actionable text; protocol errors are JSON-RPC errors. Tools must not vary per connection but may vary by the authorization on the request. Servers must validate inputs, apply access controls, rate limit, and sanitize outputs. Source: https://modelcontextprotocol.io/specification/2026-07-28/server/tools. Confidence: High.
- Stateful tools guidance (non-normative, and the spec's own example is "a database transaction"): return an explicit handle from a creation tool, accept it on later calls, check authorization on every call, keep it opaque, state its lifetime, and report expiry as a tool execution error. A handle is a name, never a credential. Source: same page and https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices. Confidence: High.
- Resources and templates (RFC 6570 URI templates, `ttlMs` and `cacheScope` required on reads and lists, `-32602` when missing), prompts (user-invoked, argument completion through `completion/complete`, up to 100 suggestions), pagination (opaque cursors), progress (`progressToken` in `_meta`, monotonic `progress`, optional `total` and `message`), cancellation (SSE close on HTTP, `notifications/cancelled` on stdio), and caching hints (`ttlMs` at least 0, `cacheScope` public or private, never a substitute for access control). Sources: the `server/resources`, `server/prompts`, `server/utilities/pagination`, `basic/patterns/progress`, `basic/patterns/cancellation`, and `server/utilities/caching` pages under https://modelcontextprotocol.io/specification/2026-07-28/. Confidence: High.
- Elicitation through MRTR: form mode and URL mode; only for clients that declared `elicitation` in `clientCapabilities`; never for passwords, keys, or tokens; `requestState` is attacker-controlled and must be integrity-protected when it influences authorization or logic. Source: https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr and the elicitation page. Confidence: High.

## 4. The Rust SDK and crate stack

### 4.1 rmcp 3.3.0

- Registry facts: latest 3.3.0 published 2026-09-10T15:32:23Z, Apache-2.0 since 0.13.0 (MIT before), `rust-version` 1.88, edition 2024, 25.9 million downloads, 64 versions; releases 1.0.0 (2026-03-03), 2.0.0 (2026-06-29), 3.0.0 (2026-07-28, same day as the spec), 3.1.0, 3.2.0 (2026-08-31), 3.3.0. `rmcp-macros` 3.3.0 is released in lockstep. Source: https://crates.io/api/v1/crates/rmcp and https://crates.io/api/v1/crates/rmcp/versions. Confidence: High.
- Protocol support: README at the tag says "This SDK implements the stable MCP `2026-07-28` specification while remaining fully compatible with the `2025-11-25` release and earlier versions." `KNOWN_VERSIONS` lists all five dated revisions; `ProtocolVersion::LATEST` is `2025-11-25` because that is the newest revision with a handshake, and since 3.2.0 (PR #1228) any `initialize` request selects legacy semantics; `2026-07-28` is reached through `server/discover` plus per-request `_meta`. Source: https://raw.githubusercontent.com/modelcontextprotocol/rust-sdk/rmcp-v3.3.0/README.md and `crates/rmcp/src/model.rs` at the tag. Confidence: High.
- Feature flags that matter: default `base64`, `macros`, `server`; `transport-io` (stdio), `transport-streamable-http-server` (Tower service for axum or hyper), `elicitation`, `request-state` (HMAC-sealed `requestState`), `schemars`, `auth` (client side), `transport-worker` (in-process testing). No legacy HTTP+SSE server: removed in 0.11.0 and called "a deliberate non-goal". Source: `crates/rmcp/Cargo.toml` and `CHANGELOG.md` at the tag. Confidence: High.
- Server authoring: `ServerHandler` with one required method (`get_info`) and defaults for `discover`, `negotiate_initialize` (3.3.0), `list_tools`, `call_tool`, `list_resources`, `read_resource`, `list_resource_templates`, `list_prompts`, `get_prompt`, `complete`, `listen`, task methods, and notification hooks. Macros: `#[tool_router]`, `#[tool_handler]`, `#[tool(name, description, input_schema, annotations(...))]`, `#[prompt_router]`, `#[prompt_handler]`, `#[prompt]`. `Parameters<T>` derives `inputSchema` (JSON Schema 2020-12, root must be an object, cached per type); `Json<T>` sets `structuredContent`, a text fallback, and `outputSchema`; `ToolAnnotations` has builders for all four hints; `ToolRouter` supports `+` merging and runtime `disable_route` and `enable_route`, which is how access modes can hide write tools. Descriptions must be bare string literals (issue #1175). Source: https://docs.rs/rmcp/latest/rmcp/ and `crates/rmcp-macros/src/lib.rs` at the tag. Confidence: High.
- Streamable HTTP server config defaults: `allowed_hosts` localhost, 127.0.0.1, ::1; `allowed_origins` empty (set it); `sse_keep_alive` 15 seconds; `max_request_body_bytes` 4 MiB (413 above); `legacy_session_mode` true (affects only pre-2026-07-28 clients); the service factory runs per request in stateless mode, so shared state such as the PostgreSQL connection lives in a `Clone` handle captured by the closure. Source: `crates/rmcp/src/transport/streamable_http_server/tower.rs` at the tag. Confidence: High.
- Cancellation: `RequestContext.ct` is a child `CancellationToken` cancelled on `notifications/cancelled` (stdio), on stream disconnect (HTTP, since PR #967), and after the response. Progress: read `progressToken` from `ctx.meta` and call `notify_progress`. Tasks: `rmcp::task_manager::TaskManager` (in-memory), check `supports_tasks()` before returning a task; `notifications/tasks` push over `subscriptions/listen` is not wired (PR #1020). Source: README sections and `examples/servers/src/` at the tag. Confidence: High.
- Server-side auth is the application's job: the `auth` feature exposes `OAuthState`, `AuthorizationManager`, `AuthClient`, credential stores, and enterprise exchanges, all for the client role; the shipped auth examples build metadata routes and a bearer middleware by hand in axum. `rmcp-server-kit` 3.10.1 (2026-09-08, third party) layers API keys, mTLS, OAuth JWT/JWKS validation, RBAC, and rate limiting on top. Source: `crates/rmcp/src/transport/auth.rs` and `docs/OAUTH_SUPPORT.md` at the tag; https://crates.io/api/v1/crates/rmcp-server-kit. Confidence: High.
- Open issues to watch before shipping stdio: #1261 (2026-09-11, untriaged) reports a deadlock when the first request on a `2026-07-28` stdio connection emits progress or log notifications before the service loop starts; #1030 (P2) reports an unbounded stdin line buffer; #1188 returns 400 instead of 403 on a malformed Origin; #388 has no built-in rate limiting; #1067 documents feature-flag traps. Source: the issue pages under https://github.com/modelcontextprotocol/rust-sdk/issues/. Confidence: High that they are open; Medium on impact.
- Advisories: five published, all fixed by 2.1.0 (DNS rebinding CVE-2026-42559 in 1.4.0; session-table leak CVE-2026-63128, OAuth SSRF, and PRM validation in 2.0.0; header leak CVE-2026-64684 in 2.1.0). 3.3.0 carries none. Source: https://api.github.com/repos/modelcontextprotocol/rust-sdk/security-advisories?state=published. Confidence: High.
- Schema pitfall: `Option<T>` fields emit `"type": ["T", "null"]`, which some LLM hosts (Vertex AI, Azure OpenAI per a 2026-05-21 downstream report) reject. Prefer `#[serde(default)]` with concrete defaults or post-process schemas in `list_tools`. Source: https://docs.rs/rmcp/latest/src/rmcp/handler/server/common.rs.html and https://github.com/modelcontextprotocol/rust-sdk/issues/135. Confidence: Medium on breadth, High on rmcp behavior.

### 4.2 Alternatives, and why rmcp wins

- `rust-mcp-sdk` 2.0.0 (2026-08-27, 267,899 downloads, 191 stars) implements `2026-07-28` with 110/110 server conformance and ships server-side OAuth providers; `turbomcp` 4.0.0-alpha.4 (2026-09-10) serves three revisions and points readers to rmcp for the official implementation; `tower-mcp` 0.22.2 (2026-08-27, 10 stars) gates `2026-07-28` behind a feature; `pmcp` 2.20.0 (2026-09-05) has unverified coverage; `mcpkit` 0.7.0 targets `2025-11-25`; `poem-mcpserver` 0.3.1 has not shipped since 2025-10-13; `mcp-protocol-sdk`, `mcp-core`, `mcpr`, `mcp-sdk`, `mcp-rust-sdk`, `axum-mcp`, and `mcp-rs` are archived, dead, or unusable. Verdict: rmcp, the official Tier 1 SDK with 97 times the downloads of the nearest alternative and same-day spec tracking, pinned at 3.3.0 by production servers (`apollo-mcp-server`, `pgmoneta_mcp`). Source: the crates.io API and GitHub API per crate, listed in `research/02-rust-mcp-sdk-rmcp.md`. Confidence: High on facts, Medium on the verdict.

### 5.2 How read-only was enforced, and how it failed

- Engine-only `READ ONLY` with raw multi-statement strings (the reference server): bypassed with `COMMIT; DROP SCHEMA public CASCADE;` and `SET` leakage across the pool; fixed in PR #1889 (2025-05-29) with prepared statements and connection recycling, one day after the archive snapshot. Source: https://securitylabs.datadoghq.com/articles/mcp-vulnerability-case-study-SQL-injection-in-the-postgresql-mcp-server/ (2025-08-21). Confidence: High.
- Keyword allowlist plus engine read-only (DBHub): the engine layer was gated on a config value that was never populated before 0.22.6 (CVE-2026-61788, 2026-06-24: sequence tampering with an ordinary role; `lo_export`, `pg_read_file`, `dblink` plus `COPY TO PROGRAM` with a privileged one); a comment-lexing differential on MySQL (CVE-2026-61789); DNS rebinding on the HTTP transport (CVE-2026-61742). Source: the GitHub advisory API for bytebase/dbhub. Confidence: High.
- Keyword blocklists (AWS Labs, Microsoft before 2026-09-11): AWS's own words in PR #4575: "The text/regex approach was structurally unsound and had reported bypasses: SSRF via dblink ... COPY ... TO PROGRAM RCE ... Unicode-escape evasion". Microsoft in PR #3202: "That approach was both unsound (trivially bypassed, and it produced false positives on legitimate queries) and unnecessary". Confidence: High.
- Parser allowlist (Postgres MCP Pro): `RangeFunction` nodes in `FROM` skipped the function-name check, so `pg_read_file` ran through `SELECT * FROM pg_read_file(...)` (CVE-2026-85620, VulnCheck 2026-09-04, CVSS 9.2, unfixed). Confidence: High.
- The same failure class outside MCP: pgAdmin 9.16 (2026-06-18) fixed a multi-statement bypass of its `READ ONLY` wrapper chaining to RCE through `COPY TO PROGRAM` on a superuser connection; 9.17 (2026-07-30) fixed a lexer differential between `sqlparse` and PostgreSQL under `standard_conforming_strings = on`. Source: https://www.pgadmin.org/docs/pgadmin4/latest/release_notes_9_16.html and 9_17. Confidence: High.
- An independent audit (2026-07-04) bypassed read-only in 14 SQL MCP servers with `WITH` prefixes and multi-statement inputs and found DSN-supplied port scanning. Source: https://m10x.de. Category: Consensus. Confidence: Medium on breadth.
- The mitigations vendors converged on: parse with PostgreSQL's own grammar or do not parse at all; make the least-privilege role the real boundary and refuse over-privileged roles at runtime; reject multi-statement input (prepared statements, extended protocol, or a parse-tree count); recycle or isolate the session per call; scope by read-only flag, project, and category; defend HTTP listeners against DNS rebinding; sanitize untrusted content; publish honest annotations while treating them as hints. Confidence: High.

### 5.3 Prompt injection through data

- GitHub MCP "toxic agent flow" (Invariant Labs, 2025-05-26): a malicious public issue steered Claude Desktop into leaking private-repo data into a public PR. GitHub's answer: Lockdown mode, secret scanning on public-repo calls, read-only mode, per-tool selection through `X-MCP-Tools`, and default content sanitization (Unicode filtering, HTML sanitization, markdown fence filtering) on 2025-12-10. Source: https://invariantlabs.ai/blog/mcp-github-vulnerability and https://github.blog/changelog/2025-12-10-the-github-mcp-server-adds-support-for-tool-specific-configuration-and-more/. Confidence: High.
- Supabase MCP "lethal trifecta" (General Analysis, published by Simon Willison 2025-07-06): a support ticket told the agent to read `integration_tokens` and post them back; Cursor with the `service_role` key did. Supabase's answer: read-only mode, project scoping, feature groups, warnings wrapped around query results, and "Never connect AI agents directly to production data." Source: https://simonwillison.net/2025/Jul/6/supabase-mcp-lethal-trifecta/ and https://supabase.com/blog/defense-in-depth-mcp. Confidence: High.

### 5.4 What users praise and complain about

- Token cost first: DBHub 1.4k versus 19.0k (Toolbox) and 19.3k (Supabase); HenkDz merged 46 tools into 18 because "Cursor can actually discover and use them properly now"; GitHub reports 60 to 90 percent context savings from loading 3 to 10 tools; a dev.to author counted 60,000 tokens of metadata for four PostgreSQL environments as separate servers. Source: the DBHub README, https://www.reddit.com/r/mcp/comments/1kttr9n/ (2025-05-23), the GitHub changelog. Confidence: High on vendor numbers, Medium on anecdotes.
- Large schemas: pgEdge measured TSV at 30 to 40 percent fewer tokens than JSON, schema filtering cutting output by 90 percent, and a dedicated `count_rows` tool as the biggest single saver; Bytebase caps schema output at 200 tables. Source: pgEdge engineering (2026-02-18) and docs.bytebase.com. Confidence: Medium.
- Write misuse: "I'd asked the agent to 'clean up the bad records.' ... This one just ran it" (Medium, 2026-07-12); `readOnlyHint` "is a hint, not a contract"; users choose "always allow" under prompt fatigue. Confidence: Medium.
- Connection pain: IAM auth and secret plumbing were AWS's top asks; Docker-on-macOS `localhost` confusion appears in three READMEs; Postgres MCP Pro's README calls both startup-DSN and tool-supplied credentials flawed because tool-supplied ones "are passed through the LLM and stored in the chat history". Confidence: Medium.
- Praise goes to Postgres MCP Pro's tuning depth, DBHub's minimalism and SSH support, Neon's branch-based migrations, and Supabase's scoping. Confidence: Medium.

### 5.5 Gaps no surveyed server closes

- Parser-grade safety in one binary without a Python or Node runtime.
- Explicit read-only, write-only, and read-write modes with the database role as the boundary and a runtime refusal of over-privileged roles (AWS has the check; nobody has write-only).
- One-database, one-schema scoping that rejects cross-schema references.
- SSH tunnels (DBHub only).
- Destructive confirmation through the protocol (nobody uses elicitation or MRTR).
- Audit logging on by default (absent in DBHub, Postgres MCP Pro, Google Toolbox, and the reference server).
- The full lifecycle in one place: schema diff, backups, role lifecycle, index advice, health checks, and write tooling never appear together.
- Current-spec compliance: only Supabase's README claims the current revision; the best-documented Rust server targets `2025-11-25`.
- Token discipline as a design axis rather than an afterthought.

## 6. Connecting to PostgreSQL from Rust

### 6.1 Driver comparison

- `tokio-postgres` `simple_query` "returns the values in rows as strings rather than in their binary encodings", runs semicolon-separated statements in one round trip, and "preserves the framing between the separate statements"; `simple_query_raw` (0.7.15) streams the messages. `query` and `query_typed` bind parameters and ask for binary output on every column (`result_formats` set to one code of 1), which fails on types with no binary send function such as `aclitem` (maintainer comment on issue #596). `connect_raw` accepts any `AsyncRead + AsyncWrite` stream. `copy_in` and `copy_out` exist. `check_connection` and a more effective `is_closed` arrived in 0.7.15; `cancel_token` cancels a running statement from another task. Source: https://docs.rs/tokio-postgres/latest/tokio_postgres/struct.Client.html and `tokio-postgres/src/query.rs`. Confidence: High.
- `sqlx` 0.9.0 `query()` "may only contain a single DML statement" and always prepares; `raw_sql` runs scripts without parameters and "the database server will treat those statements as all executing within the same transaction block"; some decoders refuse text format; custom types inside records fall back to built-in OIDs only ("custom types in records are not fully supported yet"); MSRV 1.94.0; the repository moved from launchbadge to transact-rs. Source: https://docs.rs/sqlx/latest/sqlx/fn.raw_sql.html and https://github.com/transact-rs/sqlx/issues/1269. Confidence: High.
- Verdict: `tokio-postgres`. Confidence: High on the facts, Medium on the judgment.

### 6.2 libpq compatibility

- `tokio-postgres::Config` parses both the URI and key-value forms and supports `user`, `password`, `dbname`, `options`, `application_name`, `sslmode` (only `disable`, `prefer`, `require`), `host` (a path means a Unix socket directory; multiple hosts allowed), `sslnegotiation` (`postgres` or `direct`, needs ALPN `postgresql`), `hostaddr`, `port`, `connect_timeout`, `tcp_user_timeout`, `keepalives` (on by default, 2 hour idle), `target_session_attrs`, `channel_binding`, and `load_balance_hosts`. It does not accept `passfile`, `service`, `sslrootcert`, `verify-ca`, or `verify-full`, and reads no `PG*` environment variables (issues #654 and #729 open since 2020 and 2021). Source: https://docs.rs/tokio-postgres/latest/tokio_postgres/config/struct.Config.html. Confidence: High.
- The PostgreSQL 18 manual defines what OwnPG implements itself: the `PG*` environment variables (`PGHOST`, `PGHOSTADDR`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD` with its process-list warning, `PGPASSFILE`, `PGSERVICE`, `PGSERVICEFILE`, `PGSYSCONFDIR`, `PGOPTIONS`, `PGAPPNAME`, `PGSSLMODE`, `PGSSLROOTCERT`, `PGCONNECT_TIMEOUT`, `PGCHANNELBINDING`, `PGSSLNEGOTIATION`, and others); the password file (`hostname:port:database:username:password`, `*` wildcards, first match wins, backslash escapes, `localhost` matched for default-socket connections, ignored unless mode is 0600 on Unix, `pgpass.conf` under `APPDATA` on Windows); the service file (the per-user file, then the system file under `PGSYSCONFDIR`, INI sections, the user file wins on a duplicate name); and the precedence "A service file setting overrides the corresponding environment variable, and in turn can be overridden by a value given directly in the connection string." Source: https://www.postgresql.org/docs/18/libpq-connect.html, libpq-envars, libpq-pgpass, libpq-pgservice. Confidence: High.
- Third-party loaders are stale or copyleft: `pg-client-config` 0.1.2 (2023-08-26, Linux-only passfile), `postgres-service` 0.19.4 (2024-02-20), `pg-connection-string` and `postgres-conn-str` (AGPL-3.0-or-later). No crate named `pgpass` or `pg-service` exists. Source: the crates.io API. Confidence: High.

### 6.3 Sockets, superusers, and auth per platform

- Upstream defaults: socket directory `/tmp`, socket `.s.PGSQL.<port>`, `initdb` defaults to `trust` and names the bootstrap superuser after the OS user. Source: https://www.postgresql.org/docs/18/runtime-config-connection.html and app-initdb. Confidence: High.
- Homebrew `postgresql@18` builds 18.6 unpatched (socket `/tmp`) and runs `initdb --locale=en_US.UTF-8 -E UTF-8` as the installing user with no `-U` or `-A`, so the superuser is the macOS login user under `trust`; libpq is built with libcurl (OAuth client support). Source: https://raw.githubusercontent.com/Homebrew/homebrew-core/HEAD/Formula/p/postgresql@18.rb. Confidence: High.
- Postgres.app: a `postgres` role plus the macOS user as superuser, no password; since 2.7 a permission dialog blocks unknown passwordless client processes, so OwnPG must expect a one-time approval; the socket is `/tmp` by inference (Medium). Source: https://postgresapp.com/documentation/app-permissions.html. Confidence: High on permissions, Medium on the socket path.
- Debian and Ubuntu patch `DEFAULT_PGSOCKET_DIR` to `/var/run/postgresql`; `pg_createcluster` runs `initdb --auth-local peer --auth-host scram-sha-256`; the `postgres` OS user connects over the socket with peer auth. Source: the Launchpad commit for `51-default-sockets-in-var.patch` and `pg_createcluster` on Salsa. Confidence: High.
- RHEL, Rocky, Fedora, CentOS: sockets in both `/var/run/postgresql` and `/tmp`; `postgresql-setup --initdb`; peer for local. Arch: `/run/postgresql` and `trust` by default. Source: the CentOS `postgresql-var-run-socket.patch`, the RHEL 10 manual, the Arch PKGBUILD. Confidence: High.
- Official Docker image: `/var/run/postgresql` inside the container only; the host reaches it over TCP on the published port; superuser `postgres` (or `POSTGRES_USER`); `POSTGRES_PASSWORD` is required unless `POSTGRES_HOST_AUTH_METHOD=trust`; host connections default to `scram-sha-256` on 14 and later; from another container the host is `host.docker.internal` on macOS. Source: https://hub.docker.com/_/postgres and the 18/bookworm Dockerfile. Confidence: High.
- PostgreSQL 18 auth: `trust`, `peer`, `scram-sha-256`, `md5` (deprecated, warnings on `CREATE ROLE` and `ALTER ROLE`), `cert`, `gss`, `ldap`, and the new `oauth` method (`pg_hba.conf` plus `oauth_validator_libraries`). `tokio-postgres` supports SCRAM-SHA-256 and SCRAM-SHA-256-PLUS with `tls-server-end-point` channel binding (fixed in tokio-postgres-rustls 0.14.0); no Rust client speaks `OAUTHBEARER` yet (rust-postgres PR #1378 and sqlx PR #4400 open). Source: https://www.postgresql.org/docs/18/release-18.html and the two pull requests. Confidence: High.
- TLS: libpq's six `sslmode` values map onto rustls by hand; the default rustls `ClientConfig` already behaves like `verify-full`; `require` without a root cert needs a deliberate no-verify verifier to mirror libpq; `sslrootcert=system` means `verify-full`; `tokio-postgres-rustls` 0.14.0 has no default features (enable `ring` or `aws-lc-rs`; optional `native-certs` and `webpki-roots`). Source: https://crates.io/crates/tokio-postgres-rustls and https://www.postgresql.org/docs/18/libpq-connect.html. Confidence: High.

### 6.4 SSH tunnels

- `russh` 0.63.3 (2026-09-09, Apache-2.0, MSRV 1.89, 6.84 million downloads) supports direct-tcpip and direct-streamlocal forwarding, password, publickey, keyboard-interactive, and certificate auth, an OpenSSH agent client, known-hosts checks, keepalives, and channels usable as `AsyncRead + AsyncWrite` through `into_stream()`. The tunnel pattern: `client::connect`, authenticate, `channel_open_direct_tcpip(db_host, db_port, ...)`, `into_stream()`, then `tokio_postgres::Config::connect_raw`. Host key verification is mandatory and manual (`Handler::check_server_key` rejects all keys by default; `keys::known_hosts::check_known_hosts_path` exists). Keys with a passphrase load through `keys::load_secret_key(path, Some(passphrase))`; the agent speaks over `SSH_AUTH_SOCK`. SSH client config parsing comes from `russh-config` 0.58.0; ProxyJump chains use `client::connect_stream` over the previous hop's channel (documented by third-party crates, Medium). Source: https://docs.rs/russh/latest/russh/ and https://docs.rs/russh-config/latest/russh_config/. Confidence: High, Medium on ProxyJump.
- `openssh` 0.11.6 spawns the system `ssh` under ControlMaster, inherits every SSH client config feature, and forwards ports, but cannot hand back an in-process stream and needs an `ssh` binary. `ssh2` (libssh2, synchronous, OpenSSL) fits poorly next to tokio. `thrussh` still publishes (0.49.0, 2026-08-28) but its repository link is dead and its README says agent and encrypted-key support are not implemented. `rpg` (0.11.0) and `ferox` ship with `russh` next to `tokio-postgres`; no surveyed Rust database tool spawns `ssh -L`. Source: the crates.io API and the tools' `Cargo.toml` files. Confidence: High, Medium on the tool survey.

### 6.5 Poolers and managed endpoints

- PgBouncer 1.25.2 transaction mode never supports `SET` or `RESET`, `LISTEN`, `PREPARE` or `DEALLOCATE`, `WITH HOLD` cursors, temp tables across transactions, `LOAD`, or session advisory locks; protocol-level prepared statements work only with `max_prepared_statements` above zero; it tracks `client_encoding`, `DateStyle`, `IntervalStyle`, `Timezone`, `standard_conforming_strings`, and `application_name` (not `search_path` unless added to `track_extra_parameters`). Source: https://www.pgbouncer.org/features.html. Confidence: High.
- Supavisor: session mode on 5432, transaction mode on 6543 without prepared statements by default and without honoring `options=-c search_path` (issue #206 open). Source: https://supabase.com/docs/guides/database/connecting-to-postgres and https://github.com/supabase/supavisor/issues/206. Confidence: High.
- RDS IAM tokens are 15-minute passwords generated against the instance endpoint with `sslmode=verify-full`; Cloud SQL Auth Proxy listens on 127.0.0.1 and injects IAM tokens with `--auto-iam-authn` (plaintext to the proxy); Neon needs SNI (rustls sends it for DNS names) or `options=endpoint=<id>`. Source: the AWS, Google Cloud, and Neon documentation pages listed in `research/04-rust-postgresql-connectivity-and-ssh.md`. Confidence: High.
- `tokio-postgres` already offers the pooler-safe paths: `simple_query` and `batch_execute` prepare nothing, and `query_typed` runs an unnamed prepare-bind-execute in one round trip. Source: `tokio-postgres/src/client.rs`. Confidence: High.

### 6.6 Connection lifecycle

- Local single-user mode: one connection, the `Connection` future spawned as a task, `check_connection` or `is_closed` before use, reconnect on failure, `cancel_token` for MCP cancellation, startup `options=-c statement_timeout=... -c lock_timeout=... -c idle_in_transaction_session_timeout=...` (`transaction_timeout` on 17 and later), and `application_name=ownpg`. Remote multi-client mode: `deadpool-postgres` 0.14.2 with `RecyclingMethod::Verified`, `Manager::from_connect` for an SSH-per-connection connector, and `pool.get()` at startup to surface connection errors. `bb8-postgres` was rejected (adapter unchanged since 2025-11-24, crate from 2024-12-09). Source: https://docs.rs/deadpool-postgres/latest/deadpool_postgres/. Confidence: High, Medium on the sizing judgment.

### 7.5 Safety mechanisms

- `READ ONLY` semantics from the server source (`utility.c`, `sequence.c`, `execMain.c`, `copy.c` on `REL_18_STABLE`): blocked are `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `COPY FROM` into non-temp tables, all `CREATE`, `ALTER`, `DROP` (including `CREATE TEMP TABLE`), `COMMENT`, `GRANT`, `REVOKE`, `TRUNCATE`, `nextval()`, `setval()`, `SELECT FOR UPDATE` on non-temp tables, and `EXPLAIN ANALYZE` or `EXECUTE` of any of those. Allowed are `SET`, `SHOW`, `LISTEN`, `NOTIFY`, `PREPARE`, `EXECUTE`, `DECLARE`, `FETCH`, `VACUUM`, `ANALYZE`, `REINDEX`, `CLUSTER`, `CHECKPOINT`, `CALL`, `DO`, `LOCK`, and `ALTER SYSTEM`. Writes to remote databases through `dblink` and side effects in PL functions still happen. Confidence: High.
- Timeouts: `statement_timeout` (zero disables; starts on the first extended-protocol message), `lock_timeout` (per acquisition attempt), `idle_in_transaction_session_timeout`, `transaction_timeout` (17 and later), `idle_session_timeout` (14 and later). Source: https://www.postgresql.org/docs/18/runtime-config-client.html. Confidence: High.
- search_path: the first command of a session should be `SELECT pg_catalog.set_config('search_path', '', false)`; `ALTER ROLE ... SET search_path` for roles; `SET search_path = <schema>, pg_temp` inside `SECURITY DEFINER` functions; `REVOKE CREATE ON SCHEMA public FROM PUBLIC` on databases that predate PostgreSQL 15. Source: https://wiki.postgresql.org/wiki/A_Guide_to_CVE-2018-1058%3A_Protect_Your_Search_Path and https://www.postgresql.org/docs/15/release-15.html. Confidence: High.
- Identifiers can never be bound as parameters; build them with a `quote_ident` equivalent and bind values as `$n`; on the server, `format('%I.%I', ...)`. Source: https://www.postgresql.org/docs/18/plpgsql-statements.html. Confidence: High.
- Roles: `pg_read_all_data`, `pg_write_all_data`, `pg_monitor` (member of `pg_read_all_settings`, `pg_read_all_stats`, `pg_stat_scan_tables`), `pg_signal_backend`, `pg_maintain`, `pg_checkpoint`, `pg_create_subscription`, `pg_read_server_files`, `pg_write_server_files`, `pg_execute_server_program`. A write-only mode is not a PostgreSQL privilege model (an `UPDATE` with `WHERE` needs `SELECT` on the referenced columns), so write-only is enforced at the tool layer. Source: https://www.postgresql.org/docs/18/predefined-roles.html. Confidence: High.
- Statement classification with libpg_query node kinds (read, write, DDL, maintenance, destructive buckets) is laid out in the worker report; it is derived from the server's own read-only classifier plus the `NodeRef` enum and must be tested against real grammar coverage, especially PostgreSQL 18-only syntax that `pg_query` 6.2.0 cannot parse. Confidence: Medium.
- Reference checklists from pgAdmin 4 (table dialog tabs and constraint dialogs with a SQL preview), DBeaver (object tree, column and constraint editors, schema compare), DataGrip (create and modify dialogs with a SQL preview pane, `pg_dump` shelled out), TablePlus (structure view, pending changes), and psql (the backslash set) confirm the coverage list and add one habit worth copying: show the exact SQL before applying it. Confidence: High for pgAdmin, DataGrip, psql; Medium for DBeaver and TablePlus (undated pages).

### 8.1 Tool design rules from official sources

- Names: 1 to 128 characters in the spec, 64 or fewer for Anthropic's connector review; verb plus resource, namespaced by service (`asana_projects_search` is the engineering post's example) so tool search finds them. Source: https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/ (2026-03-16), the review criteria, and https://code.claude.com/docs/en/agent-sdk/custom-tools. Confidence: High.

## 10. Conflicts and how they were settled

- Rust SDK tier: the 2026-07-28 blog called Rust "beta"; the SDK page lists Tier 1. Both were true at their dates; rmcp 3.0.0 shipped hours after the post and PR #3287 promoted Rust on 2026-08-21. Settled by the PR and registry APIs.
- `ProtocolVersion::LATEST` is `2025-11-25` while the README claims `2026-07-28` support. Not a contradiction: `LATEST` is the newest handshake revision; `2026-07-28` has no handshake and is reached through `server/discover`. Settled from `model.rs` and PR #1228. Medium on the reading.
- cargo-dist version: GitHub and npm say 0.33.0, crates.io says 0.32.0. The GitHub release is the primary channel; `cargo install cargo-dist` gives 0.32.0. Settled by reporting both.
- Registry cargo support: issue #1423 said production rejected cargo; the docs on main document it; releases followed. Settled at Medium confidence pending a test publish.
- OWASP LLM edition: the brief named 2025; the 2026 edition (v1.0, 2026-08-03) is current with a different order. Settled by reading the PDF.
- HTTP+SSE earliest removal: the blog says "a year-long offramp"; the deprecated registry says "Three months after SEP-2596 reaches Final". Settled in favor of the registry, which calls itself the derived view of the normative notices; Medium on the exact date.
- Reference-server fix: Datadog says Anthropic fixed it on 2025-05-29; the archived copy is unpatched. Both true: PR #1889 merged one day after the archive snapshot. Settled from the GitHub API.
- Crystal DBA acquisition date: Tiger Data says 2026; Crystal DBA's own post is dated 2025-09-04. The primary wins.
- MERGE and SPLIT PARTITIONS in PostgreSQL 19: the published notes list it; the branch reverted it on 2026-08-27. The commit wins.
- PostgreSQL 19 GA: roadmap "September 2026", announcements "September/October 2026", open items "TBD". All official; no GA date exists yet.
- thrussh: assumed dead, still publishing monthly; unsuitable anyway (dead repository link, no agent or encrypted keys). Settled by the registry and README.
- Postgres.app socket path: a 2013 post says `/var/pgsql_socket`; 2024 logs and Postico's docs show `/tmp`; the app passes no socket directory to `initdb`. Settled by recency at Medium.
- Supavisor prepared statements: Supabase's guide says unsupported; the project docs describe a feature flag. Settled as unsupported by default.
- Conformance counts (67/67, 50/50, 30/30, 110/110, 35/35) measure different suites and filters; none contradicts another. Reported as is.
- Tool annotation effects: the Agent SDK docs call three hints informational; the connector review says they gate confirmation. Different surfaces (in-process SDK tools versus remote connectors). Both reported.
