## 1. Summary

OwnPG is one Rust binary that gives an AI client the full PostgreSQL DBA lifecycle over the Model Context Protocol, scoped to one database and one schema per run. It ships first as a local stdio server that connects to whatever PostgreSQL the developer already has (Homebrew, Postgres.app, Docker, a Linux package, or a server behind SSH) using the same credentials psql would use, with or without a password. The user picks read-only, write-only, or read-write access at startup, and the server enforces that choice in four layers (the database role, PostgreSQL's own SQL parser, per-call engine controls, and the tool list itself) because every keyword-based guard in the field was bypassed in 2026. A remote mode over Streamable HTTP with OAuth 2.1 comes second. OwnPG follows the MCP revision `2026-07-28`, builds on the official `rmcp` SDK, and reuses the command surface, error contract, tests, CI, and release pipeline of the `reserve` repository.

## 2. Problem

Today a developer who wants an AI assistant to look at or change a PostgreSQL database has to choose between servers that are unsafe, incomplete, heavy, or hard to connect.

- Unsafe: the read-only modes of DBHub, AWS Labs, pgEdge, Postgres MCP Pro, and pgAdmin's assistant were all bypassed between June and September 2026 (CVE-2026-61788, CVE-2026-87911 at CVSS 9.6, CVE-2026-85620 still unfixed, CVE-2026-17351). The failure was the same each time: the guard and PostgreSQL parsed the SQL differently.
- Incomplete: no single server covers schema, table, column, index, constraint, view, function, and role management plus CRUD, EXPLAIN, maintenance, and monitoring. Schema diff, backups, index advice, and health checks never appear together with write tooling.
- Heavy: the Google Toolbox loads 28 tools at about 19,000 tokens and Supabase about 19,300; Claude Code truncates tool results at 25,000 tokens and defers large tool sets behind tool search. Users report that agents stop finding the right tool past 30 to 50 tools.
- Hard to connect: the surveyed servers take one DSN or an environment variable and stop there. None except DBHub supports SSH, none reads the libpq password or service files, and several accept a connection string through a tool call, which puts credentials into the chat history.
- Behind the protocol: the current MCP revision (`2026-07-28`) removed sessions and the handshake and added `server/discover`, per-request metadata, caching hints, and a new elicitation pattern. Only Supabase's README claims the current revision; the best-documented Rust server targets `2025-11-25`.

The Principal Architect runs several PostgreSQL projects on a Homebrew install at 127.0.0.1:5432 with a `claude_dev` role and works from Claude Code, Claude Desktop, Cursor, VS Code, and Codex. He needs one tool he trusts to point at a project database, and he needs it to refuse the things an assistant should never do on its own.

## 3. Goals

- G1: One binary covers the whole DBA lifecycle for one database and one schema, with the same tool names in every client.
- G2: Read-only mode cannot be bypassed by any input the parser accepts, and the test suite proves it against the known bypass corpus (multi-statement, `WITH` prefix, `FROM`-clause functions, `COPY TO PROGRAM`, Unicode-escaped identifiers, `SET` leakage).
- G3: The default local setup works with zero configuration on Homebrew, Postgres.app, Docker, Debian and Ubuntu, RHEL, and Arch, and with one flag for a server behind SSH.
- G4: The default tool set costs the client at most 6,000 tokens of tool metadata, measured with the Inspector's `tools/list` output.
- G5: The server passes the official conformance suite for `2026-07-28` and still serves clients on `2025-11-25`.
- G6: Every executed statement lands in an audit log by default, without values or rows.
- G7: Installation takes one command on macOS, Linux, and Windows, and the server is listed in the MCP Registry as `io.github.devops-infinity/ownpg`.

## 4. Non-goals

- OwnPG does not manage MySQL, SQLite, MongoDB, or any engine other than PostgreSQL.
- OwnPG is not a terminal or graphical database client; it has no TUI and no GUI.
- OwnPG does not run more than one database or schema per process; a second project runs a second process.
- OwnPG is not a migration framework; it renders and runs DDL on request and records it, and nothing more.
- OwnPG does not host a shared multi-tenant SaaS; remote mode serves one deployment owner.
- OwnPG does not accept connection strings, passwords, or tokens through tool arguments, ever.
- OwnPG sends nothing anywhere except the configured PostgreSQL, the SSH bastion the user named, and, in OAuth mode, the identity provider's key endpoint. No telemetry, no crash reporting, no update check.

## 5. Users

- The Principal Architect: full-stack engineer, Dhaka, several projects, PostgreSQL 18 on Homebrew, daily use from Claude Code and Claude Desktop, occasional Cursor, VS Code, and Codex. Expert level. Needs read-only for exploration and read-write for schema work on local databases, and SSH to staging servers.
- Developers on the same team or on other projects: comfortable with psql and Docker, use one or two AI clients, want the server to "just connect" the way psql does. Intermediate level. Daily use in read-only, occasional write.
- Operators and DBAs: manage staging or production databases behind bastions, want remote mode with OAuth and strict roles, and want an audit trail. Expert level. Weekly use.
- Scripts and CI: call the binary with `--mode read-only` for schema checks in pipelines. Machine users. Need stable tool names, machine-readable output, and exit codes.

## 6. User stories

- "I open Claude Code in a project, run `claude mcp add ownpg -- ownpg serve --database myapp --schema public`, and it connects to my Homebrew PostgreSQL as my macOS user with no password, because that is how psql connects."
- "I ask the assistant what tables exist, what columns and indexes `orders` has, and how big it is, and it answers from the catalog without loading the whole schema into context."
- "I ask for the ten slowest queries and an EXPLAIN of one of them, and I get the plan and a plain-language reading of it."
- "In read-only mode I ask the assistant to fix a row by mistake, and the server refuses before PostgreSQL even sees the statement, and tells me which mode would allow it."
- "In read-write mode I ask it to add a NOT NULL column with a default, and it shows me the exact SQL first, then runs it only after I confirm."
- "I ask it to drop a table, and it asks me through the client to confirm; in a client that cannot ask, it refuses until I pass `confirm: true` to the tool."
- "I point it at staging through our bastion with `--ssh deploy@bastion.example.com` and my SSH agent, and it works like `psql` over a port forward, without me opening one."
- "I run `ownpg doctor` and it tells me which socket it found, which role it connected as, that the role is a superuser and that read-only mode therefore rests on the parser and the transaction guard, and that `pg_dump` is on PATH."
- "I run it in Docker on my laptop and it tells me to use `host.docker.internal` when `localhost` fails from inside a container."
- "I deploy remote mode behind Caddy with WorkOS AuthKit, add it to claude.ai as a custom connector, and sign in with OAuth."
- "Every statement the assistant ran today is in a JSON-lines file I can grep, with the tool name, the mode, the statement hash, the duration, and the row count, and no values."

## 7. Functional requirements

Connection and configuration

- FR-1: The server connects to PostgreSQL over a Unix socket or TCP from a libpq connection URI or a key-value DSN, using `tokio-postgres`, and sets `client_encoding` to UTF8 at connection start.
- FR-2: The server reads the libpq environment variables (`PGHOST`, `PGHOSTADDR`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`, `PGPASSFILE`, `PGSERVICE`, `PGSERVICEFILE`, `PGSYSCONFDIR`, `PGOPTIONS`, `PGAPPNAME`, `PGSSLMODE`, `PGSSLROOTCERT`, `PGCONNECT_TIMEOUT`, `PGCHANNELBINDING`, `PGSSLNEGOTIATION`), the libpq password file, and the libpq service file with libpq's precedence (connection string over service file over environment over defaults). The password file is ignored unless its mode is 0600 on every Unix (the check is skipped on Windows, as libpq does), its contents are never printed or logged, and each libpq file is read through a 1 MiB cap.
- FR-3: When no host is given, the server tries the platform socket directories in order (`/tmp`, `/var/run/postgresql`, `/run/postgresql`) as the current OS user, then `127.0.0.1:5432` as `postgres`, and `doctor` reports every attempt and its outcome.
- FR-4: The server supports the `trust`, `peer`, `scram-sha-256` (with channel binding), `md5` (with a deprecation notice), and `cert` authentication methods, and every libpq `sslmode` value (`disable`, `allow`, `prefer`, `require`, `verify-ca`, `verify-full`) plus `sslrootcert` (including `system`) mapped onto rustls. The default is `prefer`, as in libpq; `require` without a root certificate connects unverified, as libpq does; under `verify-ca` and `verify-full` with no `sslrootcert` the platform trust store is used with `webpki-roots` as the fallback when the store is empty; and OwnPG prints one stderr warning per process whenever a TLS connection is unverified or `sslmode=disable` is in effect.
- FR-5: The server opens an in-process SSH tunnel with `russh` from a host, port, user, key file (with passphrase), SSH agent, or password, verifies the host key against the known-hosts file and refuses unknown keys unless the user opts into trust-on-first-use, resolves SSH client config aliases, supports ProxyJump chains, applies a 10 second connect timeout, and offers a `system` mode that uses the installed `ssh` binary instead.
- FR-6: Connection profiles live in a TOML file with 0600 permissions under the OwnPG config directory (an XDG-style path on macOS and Linux, the roaming application data folder on Windows). The file carries `format = 1`; a missing format reads as 1, a higher unknown format is refused with an upgrade message, and unknown keys are refused with the file, line, and key named. A profile may hold a plain-text password (the file is refused when its mode is looser than 0600), or it may name a keychain entry or an environment variable instead. Settings resolve as CLI flags over `OWNPG_*` environment variables over the profile over libpq sources over built-in presets, in one function that returns one immutable `Settings` value; `--config <file>` and `OWNPG_CONFIG` replace the search; `config show` prints every setting with its origin and masks secrets as `set`.
- FR-7: A `pooled` setting (auto-detected from PgBouncer or Supavisor ports when possible) switches the server to pooler-safe behavior: `SET LOCAL` inside transactions, no named prepared statements, no `LISTEN`, and channel binding `prefer` instead of `require`.
- FR-8: The server sets `application_name=ownpg/<version>`, `statement_timeout`, `lock_timeout`, and on PostgreSQL 17 and later `transaction_timeout` at connection start from configurable values, derives `idle_in_transaction_session_timeout` from the transaction handle expiry (expiry plus five seconds, so a handle always expires before the server aborts it), checks the connection before each call, and reconnects once after a drop; a reconnect never resumes an open handle (see FR-22).
- FR-9: `serve` connects at startup; when PostgreSQL is unreachable it exits with the external-failure class and a message naming what was tried, and `doctor` is the diagnostic path.

Scope and access modes

- FR-10: Each run binds to one database and one schema (default `public`), resolved through the layers in FR-6 (`--database`, `OWNPG_DATABASE`, the profile, or `PGDATABASE`); an unresolved database exits with the usage class and names the flag. The session's first statement pins `search_path` to that schema (or to empty with fully qualified names when pooled), and every generated statement qualifies object names with the scoped schema.
- FR-11: The access mode is one of `read-only`, `write-only`, or `read-write`, chosen at startup. The default tool set (FR-17) loads in every mode; the `write` and `transactions` groups load automatically in `write-only` and `read-write`; the `ddl`, `roles`, `maintenance`, `monitoring`, and `host` groups load only when named in `--tools` or the profile and only in a mode that allows them; `tools/list` returns the loaded tools in a fixed order. One table in the source (`groups.rs`) lists every tool with its group, allowed modes, required remote scope, and annotations, and a test asserts every tool appears once and every group has a scope.
- FR-12: At startup the server reads the connected role's attributes and memberships and reports superuser, `rds_superuser`, and `BYPASSRLS`; with `strict_role = true` (the default in remote mode) it refuses to start on such a role, and with the local default it warns in `doctor` and marks every audit record.
- FR-13: Before execution, every statement is parsed with `pg_query` (libpg_query); the server counts statements and refuses more than one per call, classifies the parse tree as read, write, DDL, maintenance, or destructive, and refuses any class the mode does not allow. A parsed single statement runs through the simple query protocol so every column returns as text. A statement the parser cannot parse is refused in `read-only` and `write-only` modes; in `read-write` mode it runs through the extended query protocol, so PostgreSQL itself refuses a batch, and the audit record is flagged `unparsed`.
- FR-14: In `read-only` mode every statement runs inside `BEGIN READ ONLY` with a rollback at the end, and the classifier also refuses `ALTER SYSTEM`, `CALL`, `DO`, `VACUUM`, `REINDEX`, `CLUSTER`, `LOCK`, `NOTIFY`, and `SET` (except the server's own settings), because PostgreSQL allows those in a read-only transaction.
- FR-15: In `write-only` mode a top-level `SELECT` is refused while `INSERT`, `UPDATE`, `DELETE`, `MERGE`, and `COPY FROM STDIN` are allowed, including their `RETURNING` clauses.
- FR-16: The classifier flags as destructive: `DROP`, `TRUNCATE`, `DROP DATABASE`, `DROP ROLE`, `DROP OWNED`, `ALTER TABLE` with drop column, drop constraint, detach partition, type change with `USING`, or set unlogged, `DELETE` or `UPDATE` without a `WHERE` clause or with a constant-true one, `COPY` to or from a file or `PROGRAM`, and any reference to an object outside the scoped schema other than `pg_catalog` and `information_schema` reads.

Tools

- FR-17: The default tool set is `pg_list_objects`, `pg_describe`, `pg_run_query`, `pg_count`, `pg_explain`, `pg_health`, and `pg_doctor`. `pg_list_objects` takes `object_types` (a closed list), `name_pattern` (a bound `LIKE` parameter with `%` allowed), and `detail_level`, caps the result at 200 objects with `truncated = true` and a cursor beyond that, and sorts by schema then name with the OID as the tie-break. `pg_describe` returns a table's columns, defaults, generated and identity columns, constraints, indexes with validity, triggers, policies, comments, size, and estimated rows, and describes views, materialized views, sequences, functions and procedures, types, extensions, roles, and privileges, using the same catalog queries psql uses. Every list and monitoring tool states its sort order and tie-break key so repeated calls return the same order.
- FR-18: `pg_run_query` runs a single read statement with a row cap (default 100, maximum 1,000), a byte cap, and pagination through a server-side cursor (`DECLARE CURSOR` inside the read transaction) exposed as an opaque cursor handle with a short expiry, and returns compact text plus `structuredContent` with a declared `outputSchema`. All paged tools share the argument names `cursor` and `row_cap` and the result fields `rows`, `truncated`, `cursor`, and `estimate`. `pg_count` returns the `reltuples` estimate by default and an exact count on request. `pg_explain` supports `ANALYZE`, `BUFFERS`, `SETTINGS`, `WAL`, `GENERIC_PLAN`, `MEMORY`, `SERIALIZE`, and `FORMAT JSON`, and runs `ANALYZE` of a write only inside a transaction that rolls back.
- FR-19: Write tools cover insert, update, delete, merge, and upsert with `RETURNING` (including `OLD` and `NEW` on PostgreSQL 18), a general write-statement tool `pg_run_write`, and `pg_copy` for `COPY` in and out over the connection only (text and CSV; binary `COPY` is refused with a message naming `pg_dump`); write tools are absent in `read-only` mode and read tools are absent in `write-only` mode.
- FR-20: DDL tools (`pg_table`, `pg_column`, `pg_constraint`, `pg_index`, `pg_view`, `pg_sequence`, `pg_routine`, `pg_trigger`, `pg_type`, `pg_extension`, `pg_comment`) cover databases and schemas, tables (regular, temporary, unlogged, partitioned, `LIKE`, inheritance), columns (add, drop, rename, type change with `USING`, default, `NOT NULL`, identity, generated, statistics, storage, compression, comment), constraints (primary key, unique with `NULLS NOT DISTINCT` and `WITHOUT OVERLAPS`, check, foreign key with actions and `PERIOD`, exclude, named `NOT NULL`, `NOT VALID` then `VALIDATE`, deferrable, `ENFORCED` and `NOT ENFORCED`), indexes (all six methods, unique, concurrent, partial, expression, `INCLUDE`, reindex), views and materialized views (refresh, concurrently), sequences, functions and procedures (SQL, PL/pgSQL, security definer with pinned `search_path`), triggers and event triggers, enum, composite, domain, and range types, extensions, and comments. Every DDL tool takes an `operation` enum with conditional validation that reports every failing field at once, renders the exact SQL from typed arguments through an identifier-quoting renderer, supports `dry_run`, and treats statements that cannot run in a transaction (`CREATE INDEX CONCURRENTLY`, `REINDEX CONCURRENTLY`, `VACUUM`, `CREATE DATABASE`) correctly. An enum `ADD VALUE` that the same call would use is refused with the SQLSTATE 55P04 explanation and a request to run two calls, because a value can never be removed again.
- FR-21: Role tools (`pg_role`, `pg_grant`, `pg_policy`, `pg_privileges`) create, alter, and drop roles, grant and revoke privileges on tables, sequences, schemas, routines, databases, and parameters, set default privileges, manage role membership with `ADMIN`, `INHERIT`, and `SET` options, manage row-level security policies, list privileges, and apply least-privilege templates for the three access modes.
- FR-22: `pg_transaction` returns an opaque handle from `begin`, accepts it on `commit`, `rollback`, `savepoint`, and `rollback_to` (savepoint names are client-supplied identifiers validated by the renderer), binds the handle to the calling principal and refuses any other principal, and tracks a state of `open`, `expired`, `committed`, `rolled_back`, or `lost` with a written transition table: `commit` or `rollback` on a non-open handle is a tool error naming the state, expiry rolls the transaction back, and a connection drop marks every handle on that connection `lost`. Local mode allows one open transaction handle and at most eight cursor handles, and opens a second connection lazily for reads and catalog tools while a transaction handle is open (capped at two connections); remote mode allows one transaction handle per principal, bounded by the pool.
- FR-23: Maintenance tools (`pg_vacuum`, `pg_analyze`, `pg_reindex`, `pg_refresh`, `pg_vacuum_needs`, `pg_backend`) run `VACUUM` (all options), `ANALYZE`, `REINDEX`, `CLUSTER`, `CHECKPOINT` (when the role allows), and `REFRESH MATERIALIZED VIEW`, each under a per-tool `SET LOCAL statement_timeout`, report which tables need vacuum from `pg_stat_user_tables` using the autovacuum threshold formula with per-table overrides, and cancel or terminate a backend through `pg_signal_backend`.
- FR-24: Monitoring tools (`pg_activity`, `pg_locks`, `pg_replication`, `pg_wal`, `pg_indexes_health`, `pg_bloat`, `pg_settings`, `pg_top_queries`) report activity and long transactions, locks and blocking chains, replication status and slots, WAL and checkpoint statistics, cache hit ratio, connection use, transaction-ID age, invalid, duplicate, and unused indexes, estimated bloat (with the estimator's caveat and `pgstattuple` when installed), settings, and top queries from `pg_stat_statements` when installed, and `pg_health` combines them into one summary.
- FR-25: Host-binary tools (`pg_dump`, `pg_dumpall_globals`, `pg_restore`, `pg_basebackup`, `pg_upgrade_check`) run the PostgreSQL binaries as subprocesses when they exist on the host running OwnPG, resolved through a `pg_bindir` setting or an absolute `PATH` entry (relative entries are skipped), started with a cleared environment that carries only `PATH`, `HOME`, and the `PG*` set, with every argument in `--option=value` form and `--` before any user-supplied name, with `--dbname` and `--schema` pinned to the scoped values, with an explicit `output_dir` argument or profile setting (never a default under the data directory), with output files written 0600, and with the exit status checked and a failure reporting the program and its arguments without secrets; the tools are absent when the binaries are missing, and `doctor` prints each resolved absolute path and version. `pg_dumpall_globals` and `pg_basebackup` are cluster-scoped by nature and say so in their descriptions.
- FR-26: Catalog data is also exposed as resources with RFC 6570 URI templates (`postgres://{database}/{schema}`, `postgres://{database}/{schema}/{table}`) carrying `ttlMs` (60,000) and `cacheScope` (`private`); a successful DDL call invalidates the cached description of the object and the schema listing; and guided DBA workflows are exposed as prompts with argument completion.
- FR-27: Every result set is wrapped with a fixed notice that row contents are data and never instructions, control and invisible characters are stripped from returned text, text is cut on a grapheme boundary when a cap applies, and truncation is reported with the cap that applied.

Protocol and transports

- FR-28: The server implements MCP `2026-07-28`: `server/discover`, per-request `_meta` handling, `resultType` on every result, `ttlMs` and `cacheScope` on every list and read result, deterministic `tools/list`, and the renumbered error codes; it also answers the `2025-11-25` `initialize` handshake for older clients. A deprecated tool stays listed for two minor releases with a description that starts with `Deprecated:` and names the replacement and the removal version.
- FR-29: Recoverable outcomes (a refused statement, a SQL error, an expired handle, a missing extension, a missing binary, a validation failure) are `isError: true` results whose `structuredContent` carries `code` (the stable error id), `rule`, `sqlstate` when present, and `remedy`; malformed arguments and unknown tools are JSON-RPC errors. Every tool argument struct rejects unknown fields, and optional arguments carry concrete defaults so no schema emits a `null` union.
- FR-30: stdio is the default transport: JSON-RPC on stdout only, logs on stderr, and when stdin is a terminal one stderr line saying the server is waiting for an MCP client. Cancellation through `notifications/cancelled` issues the PostgreSQL cancel request for the running statement. On stdin EOF or SIGTERM the server cancels the running statement, rolls back open handles and writes their audit lines, terminates child processes, flushes the audit sink, and exits 0 within one second; SIGINT at a terminal does the same and exits 130; a second signal exits at once.
- FR-31: Streamable HTTP is available behind `serve --http`: one POST endpoint, JSON or request-scoped SSE with keep-alives, validation of `MCP-Protocol-Version`, `Mcp-Method`, and `Mcp-Name` against the body, `Origin` and `Host` validation, 405 on GET and DELETE, a request body cap, a rate limit of 60 calls per minute per token and per client address answered with 429 and `Retry-After`, a health endpoint outside `/mcp` that answers `live` when the process is up and `ready` only when PostgreSQL (and, in OAuth mode, the key endpoint) is reachable, graceful shutdown that drains in-flight calls under a deadline, and binding to 127.0.0.1 unless the user names another address.
- FR-32: Remote authorization follows the `2026-07-28` authorization specification: the server publishes Protected Resource Metadata, validates bearer tokens (JWT through JWKS, or introspection when the identity provider requires it) and their audience against its own URL, answers 401 with a `WWW-Authenticate` challenge carrying `resource_metadata` and `scope`, answers 403 `insufficient_scope`, maps scopes to tool groups (`ownpg:read` for the default set and `monitoring`, `ownpg:write` for `write` and `transactions`, `ownpg:ddl`, `ownpg:roles`, `ownpg:maintenance`, `ownpg:host`), and never passes a token through; the JWKS client applies a 10 second connect and 30 second overall timeout, a 1 MiB response cap, honors `HTTPS_PROXY`, sends `ownpg/<version>` as its user agent, caches keys for the response's cache window, refreshes on an unknown key id at most once per minute, and fails closed with 401 when the endpoint is unreachable. A `bearer` mode accepts configured static tokens (from a 0600 file or the environment, compared in constant time, each bound to a mode) for private deployments; `--auth none` is allowed only on a loopback address. The authorization server is an external identity provider that supports PKCE S256 and Client ID Metadata Documents; WorkOS AuthKit is the documented first choice.
- FR-33: Destructive operations ask for confirmation through MRTR elicitation when the client declared `elicitation`, with the `requestState` sealed by a key generated per process (or read from a 0600 file in the data directory only when several remote instances share the state); otherwise the call requires `confirm: true`; `dry_run: true` always returns the rendered SQL without running it.
- FR-34: Long operations report progress when the client sent a `progressToken` and stop when the request is cancelled.

Command line

- FR-35: The binary offers `serve` (default, stdio; `--http` for the HTTP transport; `--tools` for the opt-in groups; `--mode`, `--database`, `--schema`, `--profile`, `--ssh`, `--ssh-mode`, `--ssh-trust-new-host`, `--bind`, `--auth` as `ValueEnum` or typed values with `value_name` and value hints), `doctor` (a `checks[]` array in `--format json`, exit 0 with warnings and 1 when a required check fails), `config show` (`--format json`, origins, masked secrets), `config path`, `config init` (refuses to overwrite without `--force`, supports `--dry-run`), `config set-password <profile>` (reads without echo from a terminal or from stdin, never from an argument), `config unset-password <profile>`, `config cache-clear`, `man`, `completions`, `--version` (version, short commit, build date from `SOURCE_DATE_EPOCH`, or `unknown` for a crates.io install), `-v` and `-q` (which compose with `RUST_LOG`), `--no-input` (implied by `CI=true`), `--log-format text|json`, `--log-file`, and `--config <file>`. Every command follows the `reserve` conventions: one clap tree without inferred subcommands or aliases, `--help` and `--version` on stdout with exit 0 at every level, a help footer with the issues URL and the docs URL, declared conflicts (`--http`-only flags against stdio, `--auth none` against a non-loopback `--bind`, `--ssh-mode system` against `--ssh-trust-new-host`), `hide_env_values` on flags whose environment variable can carry a secret, the stderr error shape (`error:`, `caused by:`, `try:`, `code:`), and exit classes 0 (success), 1 (runtime failure), 2 (usage or configuration), 4 (refused by policy: mode, role, host key), 5 (external failure: connect, SSH, subprocess, audit sink), 130 (interrupt). A warning never changes the exit code. Backtraces follow `RUST_BACKTRACE` and are off by default; the panic hook prints the version, the build stamp, and the issues URL, and never a path or a secret.

Audit and observability

- FR-36: An append-only JSON-lines audit log records every tool call with `v` (1), `request_id` (the `_meta` trace id when present, otherwise generated, shared with the stderr span), `timestamp` (RFC 3339 with offset), `tool`, `operation`, `mode`, `transport`, `principal` and `principal_kind` (`local`, `os_user`, `token_subject`, `bearer`), `database`, `schema`, `statement_class`, `statement_hash` (the `pg_query` fingerprint in hex) or the normalized statement when short, `decision` (`allowed`, `refused`, `dry_run`, `confirmed_argument`, `confirmed_elicitation`, `unparsed`), `rule`, `handle_id`, `duration_ms` (integer), `row_count`, `truncated`, `outcome` (SQLSTATE on error), `superuser`, and `prev` (the SHA-256 of the previous line, so tampering is evident; each rotation starts a new chain with a marker line). It never records parameter values, row data, passwords, or tokens. It is on by default under the OwnPG data directory as a 0600 file opened once in append mode, one file per process (named by profile and process id) so concurrent servers never interleave, rotated by size with a configurable cap, and can point at another path or be turned off. The README states that the log holds principal identifiers, documents the erasure procedure (stop the server, filter the file by principal, rotate), and gives a `logrotate` example.
- FR-37: Logs go to stderr through `tracing` with `RUST_LOG` control on stdio (text by default, JSON with `--log-format json`, and an optional rotating `--log-file` under the state directory), and OpenTelemetry export is available in HTTP mode with counters (calls by tool and decision, refusals by rule), a duration histogram per tool, and an open-handles gauge; `_meta` trace context is forwarded.

Documentation

- FR-38: The README carries verified configuration snippets for Claude Code, Claude Desktop (including the MCPB bundle), claude.ai custom connectors, Cursor, VS Code, Codex CLI, Gemini CLI, Zed, Windsurf, and JetBrains, the tool reference (name, purpose, input schema, output shape, one worked call, the `isError` codes it can return), the profile key reference (type, default, precedence), the exit codes, the environment variables, the audit log format with one example line, the measured token cost of the default set with the date and model of the measurement, the supported PostgreSQL versions, the minimum OS versions, an uninstall section (binary, receipt, the three directories, keychain entries, shell edits), and the maintenance statement (one maintainer and publisher, bug reports through the releases repository, no outside code contributions).

## 8. Non-functional requirements

- NFR-1 Security: read-only mode passes the bypass corpus in G2 with zero failures; the granted role for read-only mode has no `pg_read_server_files`, `pg_write_server_files`, `pg_execute_server_program`, or `dblink` access in the templates; secrets never appear in logs, output, command lines, or URLs, and a test proves that a configured password, a password-file entry, and a credentialed proxy URL never reach `doctor`, `config show`, or an error message; HTTP mode refuses to bind to a non-loopback address without authentication; the code is reviewed against OWASP LLM Top 10 2026 (LLM01, LLM02, LLM03, LLM06), OWASP MCP Top 10 v0.1 (MCP01, MCP02, MCP05, MCP07, MCP08), OWASP ASVS 5.0 (V2 and V3 for the HTTP surface), the OWASP API Security Top 10 2023, and the CWE Top 25 2025; `SECURITY.md` carries the stdio-mode threat model from phase 1 (data flows between the client, the server, PostgreSQL, the SSH bastion, and local files), the remote-mode threat model from phase 4, remediation targets (critical within 7 days, high within 30, others in the next minor), and the private disclosure channel; CI runs a secret scan on every diff and fuzz targets on the classifier, the result sanitizer, and the password-file, service-file, known-hosts, and SSH-config parsers; and before 1.0 a black-box run from another host exercises the public endpoint with a rebinding `Origin`, a wrong-audience token, an oversized body, GET, and DELETE.
- NFR-2 Correctness: the server passes the official conformance suite for `2026-07-28` and the `2025-11-25` legacy scenarios, the Inspector CLI lists and calls every tool, and a golden `tools/list` snapshot per mode and group pins names, annotations, and schemas.
- NFR-3 Compatibility: PostgreSQL 14 through 18 are supported with feature gates on `server_version_num` (16 for `pg_stat_io`, 17 for `MERGE RETURNING`, `transaction_timeout`, and `pg_stat_checkpointer`, 18 for `RETURNING OLD` and `NEW`, `NOT ENFORCED`, virtual generated columns); PostgreSQL 19 is best effort until GA. Eight targets ship: macOS (Apple Silicon and Intel), Linux glibc (x86_64 and aarch64), Linux musl (x86_64 and aarch64, fully static), and Windows MSVC (x86_64 and aarch64). Minimum platform floors are recorded in the README at the first cross-build (targets: macOS 12, Windows 10, and the glibc version the Linux build container provides) and every target is checked with `cargo check --target` in CI, including the C build of libpg_query that `pg_query` carries.
- NFR-4 Performance: startup to the first `server/discover` answer under 200 milliseconds and a catalog describe of a 200-table schema under one second, both measured on the reference laptop with the shipped `dist` binary and recorded by CI as a startup-time check; result shaping never buffers more than the byte cap in memory; role attributes, the feature map, and host-binary discovery load lazily on the first call that needs them.
- NFR-5 Token budget: the default tool set (seven tools) costs at most 6,000 tokens of metadata; each opt-in group (`write`, `transactions`, `ddl`, `roles`, `maintenance`, `monitoring`, `host`) adds its cost only when loaded, and the README publishes the measured cost per group; every description is under 2 KB.
- NFR-6 Reliability: a dropped PostgreSQL connection is detected before the next call and reconnected once; an expired or lost transaction handle produces a tool error, never a hang; every long statement honors cancellation; a stdio server uses the `current_thread` runtime and an HTTP server the multi-thread runtime; blocking work (`pg_query` parsing, keychain access, file-mode checks) runs on the blocking pool; tasks live in a `JoinSet` and no lock is held across an await; internal channels are bounded; the remote pool defaults to four connections.
- NFR-7 Maintainability: the workspace mirrors `reserve` (crate split, lint deny-list with member opt-in and negative priority, `Origins`, error contract, tests, CI); `ownpg-core`'s `config`, `classify`, `render`, `shape`, and `audit` modules import neither `rmcp` nor `tokio_postgres`; `ownpg-core/src/lib.rs` re-exports only the settings, error, server builder, and handle types; one handler module per tool group; no comments beyond the house ceiling; every `#[allow]` is item-level with a reason; `cargo fmt`, `cargo clippy` with `-D warnings` and `--all-features`, `cargo nextest`, `cargo test --doc`, `cargo doc` with `-D warnings`, `cargo deny`, `cargo audit --deny warnings`, `cargo machete`, `cargo about`, `cargo semver-checks` on `ownpg-core`, `insta` snapshots with `INSTA_UPDATE=no`, and `cargo llvm-cov` at an 80 percent floor pass on every change; a `docs/debt.md` list is reviewed at every phase exit.
- NFR-8 Supply chain: `Cargo.lock` committed, `--locked` everywhere, every dependency resolved at install time and checked against crates.io, every CI action and cargo subcommand pinned to a full SHA or exact version, a CycloneDX SBOM and a third-party attribution file in every archive, `cargo auditable` metadata embedded in the binary and scanned with `cargo audit bin`, and a `minisign` signature over the checksum file of every release (artifacts are built by hand on the Principal Architect's machine, as `reserve`'s are, so GitHub provenance attestations do not apply).
- NFR-9 Privacy: the server sends nothing anywhere except the configured PostgreSQL, the named SSH bastion, and, in OAuth mode, the key endpoint; there is no telemetry; the audit log's personal identifiers are documented with their keep window and erasure path.
- NFR-10 Accessibility and localization: not applicable to a headless server; help text and errors are plain US English; terminal output uses the eight base colors only, never carries meaning by color alone, and uses no box drawing or emoji.

## 9. Acceptance criteria

- FR-1: Given a Homebrew PostgreSQL 18 listening on `/tmp/.s.PGSQL.5432`, when `ownpg serve --database app --schema public` starts with no other flags, then it connects as the macOS login user over the socket and `server/discover` returns the server identity.
- FR-2: Given a password file with mode 0644 that holds a matching entry, when the server starts, then it ignores the file, logs "password file ignored: permissions", and does not print the file's contents.
- FR-2: Given `PGSERVICE=staging` and a service file naming a host and user, and a connection string that sets only the database, when the server starts, then the host and user come from the service file and the database from the connection string.
- FR-3: Given a Debian host where the socket lives in `/var/run/postgresql`, when no host is configured, then `doctor` shows `/tmp` tried and failed, `/var/run/postgresql` tried and connected, and the role it connected as.
- FR-4: Given a server that requires `scram-sha-256` and TLS, when `sslmode=verify-full` and a root certificate are configured, then the connection succeeds with channel binding, and when the certificate host name does not match, then the connection fails with an error that names the mismatch.
- FR-4: Given `sslmode=require` and no root certificate, when the server connects, then the connection is encrypted and unverified and exactly one warning line appears on stderr for the process.
- FR-5: Given a bastion whose host key is not in the known-hosts file, when `--ssh user@bastion` is given without trust-on-first-use, then the server refuses to connect and prints the fingerprint and the flag that would accept it.
- FR-5: Given a bastion key in the known-hosts file and an SSH agent holding the key, when `--ssh user@bastion --host 10.0.0.5` is given, then the PostgreSQL connection runs through a direct-tcpip channel and `doctor` shows "via SSH".
- FR-6: Given a profile file with mode 0644, when the server starts, then it refuses the file and names the required mode.
- FR-6: Given a profile that sets `mode = "read-only"` and an environment variable `OWNPG_MODE=read-write` and the flag `--mode read-only`, when `config show` runs, then it prints `mode = read-only (flag)`.
- FR-6: Given a profile with a misspelled key `strict_rol`, when the server starts, then it refuses the file and names the file, the line, and the unknown key.
- FR-6: Given a profile with `format = 2`, when the server starts, then it refuses the file and names the upgrade needed.
- FR-7: Given a Supavisor transaction-mode endpoint, when `pooled = true`, then the server issues `SET LOCAL search_path` inside each transaction and never `SET` at session level.
- FR-8: Given a connection killed by `pg_terminate_backend` with no open handle, when the next tool call arrives, then the server reconnects once and the call succeeds.
- FR-9: Given no reachable PostgreSQL, when `serve` starts, then it exits with class 5 and a message listing the sockets and addresses it tried.
- FR-10: Given a scoped schema `app`, when a read query references `other.customers`, then the classifier refuses it with "object outside scoped schema".
- FR-10: Given no `--database`, no `OWNPG_DATABASE`, no profile database, and no `PGDATABASE`, when `serve` starts, then it exits with class 2 and the usage text names `--database`.
- FR-11: Given `--mode read-only`, when `tools/list` is called, then exactly the seven default tools appear, in the same order on every call; given `--mode read-write` and no `--tools`, then the `write` and `transactions` groups appear as well and no DDL, role, maintenance, monitoring, or host tool does.
- FR-12: Given a superuser role and `strict_role = true`, when the server starts, then it exits with class 4 and a message naming the role attribute; given the same role and the local default, then it starts and `doctor` prints a warning.
- FR-13: Given the input `SELECT 1; DROP TABLE t`, when any tool receives it, then the call is refused as a multi-statement input before any statement reaches PostgreSQL.
- FR-13: Given `SELECT * FROM pg_read_file('/etc/passwd')` in read-only mode, when `pg_run_query` receives it, then the call is refused because the function is on the deny list, and the audit record shows the rule.
- FR-13: Given PostgreSQL 18-only syntax that `pg_query` cannot parse, when the call arrives in read-only mode, then it is refused as unparsed; when it arrives in read-write mode as `INSERT ... RETURNING WITH (OLD AS o) o.*; DROP TABLE t`, then PostgreSQL refuses the batch through the extended protocol and the audit record is flagged `unparsed`.
- FR-14: Given read-only mode and the input `SELECT nextval('s')`, when `pg_run_query` runs it, then PostgreSQL returns SQLSTATE 25006 inside `BEGIN READ ONLY` and the tool returns an `isError` result that says which mode allows it.
- FR-15: Given write-only mode, when a top-level `SELECT` arrives, then it is refused, and when `INSERT ... RETURNING id` arrives, then it runs and returns the id.
- FR-16: Given `DELETE FROM orders` with no `WHERE` clause and no `confirm`, when the write tool receives it, then it is refused as destructive and the message names the `confirm` argument and the `dry_run` option.
- FR-17: Given a table with an invalid index left by a failed concurrent build, when `pg_describe` runs, then the index is listed with `valid = false`.
- FR-17: Given a schema with 2,000 objects, when `pg_list_objects` runs with `object_types = ["table"]` and `name_pattern = "ord%"`, then at most 200 rows return, sorted by name, with `truncated = true` and a cursor when more remain.
- FR-18: Given a table with 5,000 rows and the default caps, when `pg_run_query` runs `SELECT * FROM big`, then 100 rows return with `truncated = true`, a cursor handle, and the row estimate; when the cursor is passed back, then the next 100 rows return in the same order.
- FR-18: Given read-only mode, when `pg_explain` is asked to `ANALYZE` an `UPDATE`, then the call is refused; given read-write mode, then the plan returns and the update is rolled back.
- FR-19: Given read-write mode on PostgreSQL 18, when the update tool runs with `returning_old_new = true`, then the result carries both old and new values.
- FR-20: Given a request to add an index concurrently, when `dry_run = true`, then the rendered `CREATE INDEX CONCURRENTLY` SQL returns and nothing runs; when `dry_run = false`, then the statement runs outside a transaction block and the index appears as valid.
- FR-20: Given an enum type, when a call asks to add a value and use it, then the tool refuses with the SQLSTATE 55P04 explanation and asks for two calls.
- FR-20: Given a `pg_column` call with `operation = "alter_type"` and no `new_type`, when validation runs, then one `isError` result lists every missing field.
- FR-21: Given the read-only least-privilege template, when it is applied to a new role, then the role has `USAGE` on the schema, `SELECT` on its tables, `default_transaction_read_only = on`, and membership in `pg_read_all_stats`, and nothing else.
- FR-22: Given a transaction handle idle past its expiry, when `commit` is called with it, then the tool returns an `isError` result naming the state `expired` and the work is rolled back.
- FR-22: Given a transaction handle opened by principal A, when principal B calls `commit` with it, then the call is refused and the audit line records the refusal.
- FR-22: Given an open transaction handle in local mode, when `pg_describe` is called, then it answers over the second connection and the transaction stays open.
- FR-23: Given a table whose dead tuples exceed the autovacuum threshold, when `pg_vacuum_needs` runs, then the table is listed with `needs_vacuum = true` and the computed threshold.
- FR-24: Given `pg_stat_statements` is not installed, when `pg_top_queries` runs, then it returns a tool error that names the extension and the `CREATE EXTENSION` statement.
- FR-25: Given `pg_dump` is not on PATH and no `pg_bindir`, when `tools/list` is called, then `pg_dump` is absent and `doctor` says "pg_dump: not found"; given `pg_bindir` set to the Homebrew directory, then `doctor` prints the absolute path and the version line.
- FR-25: Given a `pg_dump` call without `output_dir` and no profile setting, when the tool runs, then it refuses and names the argument; given an `output_dir`, then the file is written with mode 0600 and the result carries its path.
- FR-26: Given a client that supports resources, when `resources/templates/list` is called, then the table template appears with `ttlMs` 60000 and `cacheScope` `private`, and reading `postgres://app/public/orders` returns the same description as `pg_describe`.
- FR-27: Given a row whose text contains a zero-width character and the sentence "ignore previous instructions", when `pg_run_query` returns it, then the invisible character is stripped and the result starts with the untrusted-data notice.
- FR-28: Given a `2026-07-28` client, when it calls `tools/list`, then the result carries `resultType`, `ttlMs`, and `cacheScope`; given a `2025-11-25` client, when it sends `initialize`, then the handshake completes with `protocolVersion: "2025-11-25"`.

- FR-30: Given stdio mode, when the client closes stdin, then the process exits within one second with code 0 and nothing but JSON-RPC ever appeared on stdout; given a running statement, when SIGINT arrives at a terminal, then the cancel request is sent, the audit line is written, and the exit code is 130.
- FR-31: Given HTTP mode, when a POST arrives with `MCP-Protocol-Version: 2026-07-28` and a body whose `_meta` says `2025-11-25`, then the response is 400 with error `-32020`; when a GET arrives, then the response is 405; when the `Origin` header names another site, then the response is 403; when a client sends its 61st call inside a minute, then the response is 429 with `Retry-After`.
- FR-32: Given a token issued for another audience, when a tool call arrives, then the response is 401 with a `WWW-Authenticate` header naming the resource metadata URL; given a valid token whose scopes allow read only, when a write tool is called, then the response is 403 `insufficient_scope`; given the key endpoint is unreachable, when a token arrives, then the response is 401.
- FR-33: Given a client that declared elicitation, when a drop-table tool is called without `confirm`, then the result is `input_required` with a confirmation request and a sealed `requestState`, and the drop runs only after the client answers yes; given a client without elicitation, then the call is refused until `confirm: true` is passed.

## 12. Risks

- The parser's grammar lags PostgreSQL: `pg_query` 6.2.0 carries the 17 grammar and the 18 upgrade is an open pull request. Likelihood: high. Impact: medium. Mitigation: fail closed in read-only and write-only modes, run unparsed statements through the extended protocol in read-write mode, and track PR #79. Owner: Principal Architect.
- A parser differential bypass, the class behind CVE-2026-85620 and CVE-2026-17351. Likelihood: medium. Impact: high. Mitigation: libpg_query is PostgreSQL's own grammar; the role boundary and the `READ ONLY` transaction stay in place even when the classifier is wrong; the bypass corpus grows with every public advisory. Owner: Principal Architect.
- `pg_query` compiles libpg_query from C, so the eight cross targets need a C cross toolchain on the release machine (zig for the Linux targets, the MSVC SDK through cargo-xwin for Windows). Likelihood: high. Impact: high for the release. Mitigation: phase 0 runs `cargo check --target` for all eight before any other work and records which targets build; a target that cannot build is deferred in the release ADR rather than promised. Owner: Principal Architect.
- Local databases run as a superuser under `trust` (the Homebrew default), so read-only mode on a local install rests on the parser and the transaction guard. Likelihood: high. Impact: medium. Mitigation: `doctor` warns, audit records carry the flag, the role templates make a least-privilege role a one-command step, and `strict_role` is the default in remote mode. Owner: Principal Architect.
- rmcp issue #1261 (stdio first-request deadlock when a handler emits notifications early) and #1030 (unbounded stdin buffer). Likelihood: medium. Impact: high for stdio. Mitigation: no notifications before the first response, an application-level line cap, an integration test that sends `tools/call` as the first message, and a watch on both issues. Owner: Principal Architect.
- Clients differ on elicitation, resources, and annotations. Likelihood: high. Impact: medium. Mitigation: `confirm` and `dry_run` arguments as the baseline, tools as the primary path, and a client matrix in the README. Owner: Principal Architect.
- Token budget creep as tool groups grow. Likelihood: high. Impact: medium. Mitigation: a CI ceiling on the default set's token cost and opt-in groups. Owner: Principal Architect.
- OAuth setup complexity for a solo deployment. Likelihood: medium. Impact: medium. Mitigation: the static bearer mode for private use, a documented WorkOS AuthKit recipe, and Keycloak marked unsupported until it adds RFC 8707. Owner: Principal Architect.
- Prompt injection through row contents. Likelihood: high. Impact: high. Mitigation: closed-world tools, no outbound-network functions in the role templates, the untrusted-data notice, invisible-character stripping, and confirmation on every destructive path. Owner: Principal Architect.
- SSH host-key handling that is too lax or too strict. Likelihood: medium. Impact: medium. Mitigation: refuse unknown keys by default, print the fingerprint, and offer an explicit trust-on-first-use flag and the `system` SSH mode. Owner: Principal Architect.
- PostgreSQL 19 changes before GA. Likelihood: high. Impact: low. Mitigation: gate on `server_version_num`, keep 19 best effort in a separate scheduled workflow that is not a required check, and recheck the notes after Beta 4 on 2026-09-24. Owner: Principal Architect.
- The MCP Registry may not accept `cargo` packages in production yet. Likelihood: medium. Impact: low. Mitigation: publish the `mcpb` package type first and add `cargo` when a test publish succeeds. Owner: Principal Architect.
- MSRV drift: `russh` needs 1.89, above `rmcp` and `reserve`. Likelihood: certain. Impact: low. Mitigation: set `rust-version = "1.89"` from day one and pin the toolchain. Owner: Principal Architect.
- One maintainer, one publisher, one release machine. Likelihood: certain. Impact: high if unavailable. Mitigation: recorded in the README and the release ADR; a successor is added before the project is relied on by others. Owner: Principal Architect.

## 14. Out of scope

- Other database engines, including MySQL, MariaDB, SQLite, and MongoDB.
- A terminal or graphical interface of any kind.
- More than one database or schema in one process.
- A migration framework with versioned migration files.
- A hosted or multi-tenant service; remote mode is single-owner.
- Connection strings, passwords, or tokens as tool arguments.
- PostgreSQL 13 and older.
- The PostgreSQL 18 `oauth` client authentication method until a Rust driver speaks `OAUTHBEARER`.
- The Tasks extension, MCP Apps, sampling, and roots in 1.0.
- Windows named pipes and Windows service installation.
- Index tuning with hypothetical indexes (hypopg) in 1.0; the explain tool reports real plans only.
- Schema diff between two databases in 1.0; a schema digest of the scoped schema is in scope.
- Outside code contributions; the source is private and the public releases repository takes bug reports.
- Run-once keys for write tools; OwnPG never de-duplicates a repeated call, the sealed `requestState` is the only replay guard, and transaction handles give multi-call atomicity.
- A self-updater or an update check.
